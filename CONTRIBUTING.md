# Работа с boardgame-playroom

`main` — выпущенная версия, `dev` — интеграция. Задачи выполняются в отдельной ветке от `dev`, через PR в `dev`; обычный способ объединения — squash. Релиз — отдельный PR из `dev` в `main` с merge-коммитом (сохранение общей истории), затем fast-forward `dev` до `main` без force-push, тег и GitHub Release с проверенными файлами и SHA256SUMS.

Для первого импорта в пустой репозиторий создаётся только минимальный служебный коммит, общий для `main` и `dev`. Код поступает через обычный PR. Соседние проекты, личные сохранения, старые экспорты, секреты и локальные пути в репозиторий не входят.

Перед публикацией выполните команды из README. Полная совместная проверка приложения и игр требует обоих репозиториев; CI одного репозитория проверяет только доступную ему часть. Изменение версии API или формата сохранения требует обновления описания совместимости и проверки старой партии.

Версии приложения и игровых паков независимы. Не меняйте опубликованное содержимое под прежним тегом или номером пака. Сборки помещаются в `dist/` и прикладываются к релизу, а не коммитятся в исходники.

## Экономный запуск GitHub Actions

- Во время работы держите PR как **Draft**. Создание PR, обычный commit/push и `synchronize` **не запускают** автоматические проверки.
- Когда изменения готовы к проверке, переведите PR в **Ready for review**: один раз запустится `Application checks`; для ветки того же репозитория также выполняется read-only preflight защищённого Pages. Публикация Pages запускается только вручную. Для повторного запуска после исправлений выберите **Actions → Application checks → Run workflow** и нужную ветку; перед слиянием убедитесь, что тестируется актуальный SHA. Это не заменяет обязательных локальных тестов.
- Запускайте полный совместный тест приложения и паков при изменении игрового контракта, сетевых правил или перед выпуском. Для этого остаются команды `bash scripts/codex/check.sh --full --packs-dir PATH`; workflow `Pinned app and packs integration` используется по явному запросу, когда доступен и настроен. Запуск `Run workflow` требует, чтобы соответствующий workflow был на default-ветке GitHub; это относится и к новым экспериментальным workflow в feature-ветках.
- Сборки preview/PWA и архивы исходников создавайте непосредственно перед тестированием или выпуском, а не на каждый коммит. После изменения кода **после** последней проверки не считайте прежний зелёный статус проверкой нового HEAD.

## Стабильная линия

Приложение 0.15.0 и коллекция 0.4.0 выпускаются совместно, версии отдельных игр независимы. После проверки публикации удаляйте завершённые ветки задач; сохраняйте main, dev, исторические теги и PR. Не удаляйте уникальную работу без переноса и резервной копии. Документация текущего состояния и Roadmap имеют приоритет над историческими RC-записями.
