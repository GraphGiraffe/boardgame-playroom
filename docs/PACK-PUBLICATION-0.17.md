# Раздельная публикация 0.17

Оболочка 0.17.0 остаётся на защищённом `playroom-hod-test.pages.dev`; коллекция 0.6.0 публикуется в R2 того же Cloudflare аккаунта. Production PWA не содержит игрового кода в `installed-packs.js`: каталог `/api/packs/catalog` и файлы `/api/packs/files/...` обслуживает существующий закрытый Pages Worker через R2 binding `PLAYROOM_PACKS`. Обычный ZIP с автономным HTML остаётся снимком версий на момент сборки.

## Подготовка Cloudflare и первый переход

1. Создать приватный R2 bucket для игровых паков в том же аккаунте. Назначить в Pages project binding с именем `PLAYROOM_PACKS` на этот bucket **для production**. Указать имя bucket в GitHub variable `PLAYROOM_PACKS_BUCKET` репозитория паков. `CLOUDFLARE_ACCOUNT_ID` в репозитории паков уже заполнен. В показанной пользователем форме **Create Custom Token** создать обычный Cloudflare API Token: `Account` → `Workers R2 Storage` → `Edit`, а в `Account Resources` выбрать `Include` и конкретный аккаунт вместо `All accounts`. Записать значение Token как GitHub secret `CLOUDFLARE_API_TOKEN` репозитория паков. Publisher использует Wrangler и Cloudflare REST API: токен «R2 Object Read & Write» для S3 API ему не подходит. Более узкая группа `Workers R2 Storage Bucket Item Write` существует для токенов, создаваемых через API Cloudflare; показанная настройка в интерфейсе ограничивает обычный токен выбранным аккаунтом. Pages deploy по-прежнему использует свои прежние переменные и секреты в репозитории приложения. Закрытый Worker не попадает в публичный ZIP. Имя проекта, адрес и пароль остаются прежними.
2. Выпустить проверенную коллекцию с 12 `*.playroom-pack.json` и `SHA256SUMS` как assets GitHub Release в репозитории паков. В нём вручную запустить `Publish independent game packs`: `release=v0.6.0`, `bootstrap=true`. Его штатный GitHub token читает release assets того же закрытого репозитория. Скрипт проверит SHA256, загрузит неизменяемые файлы, скачает их обратно для сравнения, загрузит снимок каталога, затем последним шагом запишет `catalog/current.json`. Результат содержит SHA256 снимка для отката.
3. Собрать приложение командой `python3 build.py --packs-dir ../playroom-paks/packs --all-games --pwa --remote-catalog --output-dir dist/release` и выпустить проверенные `playroom-pwa.zip` и `SHA256SUMS`. Выполнить прежний защищённый Pages workflow один раз. `pages-smoke.cjs` проверяет доступность каталога и все 12 SHA256 только после входа; без входа каталог недоступен.

Cloudflare Pages advanced mode использует `_worker.js`; каталог добавлен **внутрь** существующей закрытой обёртки, поэтому отдельные файлы `/functions` не применяются. Приватный исходник обёртки остаётся только в прежнем секрете/защищённом базовом архиве. Прежде чем включать production, прогнать проверку обёртки с реальным исходником и binding.

## Последующие независимые выпуски

| Что меняется | Действие | Pages deployment |
| --- | --- | --- |
| Только оболочка | Совместный gate, новый release приложения, прежний защищённый Pages workflow | Один новый |
| Коллекция паков | Совместный gate, release паков, `Publish independent game packs` с тегом | Нет |
| Один пак | Новый release коллекции с обновлённым паком, тот же workflow с `only=<id>` | Нет |

При публикации одного пака снимок каталога наследует остальные 11 записей. Путь файла включает ID, версию и SHA256; текущий указатель меняется только после обратной проверки записанного файла и снимка. Каталог имеет `no-store`, файлы неизменяемы; приложение проверяет SHA256, manifest и API перед установкой. Сохранённая партия продолжает ссылаться на точную версию. При недоступном каталоге остаются установленные паки и последний локальный каталог. Установка новых паков остаётся явным действием в управлении играми; чистый профиль получает все 12 автоматически.

**Откат паков:** запустить тот же workflow с `rollback=<SHA256 старого снимка>`; он проверит снимок и файлы до смены указателя. **Откат приложения:** прежний Pages rollback. Снимок каталога старше сохранений не удаляет установленные версии и не переписывает уже открытую партию.

Приёмка на основном адресе: три независимых сценария, старая вкладка и PWA, несколько окон, offline, несовместимый API, испорченный SHA256, сохранения прежней версии, сетевой стол и оба отката. Локальный dry-run публикации проверяет структуру и суммы, но не заменяет проверку действующего R2 binding и сайта.
