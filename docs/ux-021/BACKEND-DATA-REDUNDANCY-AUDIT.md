## Room conversation correction and privacy

The read-scoped index is discarded on return. Every new read still resolves current membership/team; a quote target remains checked with `visible(target, ctx)` before its snippet is returned. The lookup preserves the old `.find` **first-match** behavior when different authors reuse the same message ID; using the last Map entry would have changed quote semantics. `known` metadata uses a Set while retaining strict string matching and omitting old message bodies.

The existing `presence-transport` room conversation case now checks one source read and one fresh resolve for both a reply-heavy page and known receipt/reaction updates, old quote target outside the latest80, team/spectator isolation, no audience/private reaction actor set, changed membership on the next read and the standalone live projection fallback. A blue/red author-ID collision ensures the local optimization cannot select a different private quote target. No mutation, idempotency, receipt or storage format was changed.

## SQL payloads and bounded remaining disposition

Read-only inspection of the current SQL confirms that `cloud_saves('list')` explicitly constructs metadata entries (`id/revision/checksum/summary/enabled/updated_at/deleted/bytes`), without materializing archives in the response. `get` authorizes and retrieves exactly one account-owned, nondeleted file. PUT returns current metadata, which makes the implemented batch reuse safe together with the existing expected-revision check. Quota totals and metadata use separate SELECTs under the same account settings-row lock. Removing that lock from reads is not accepted here: multi-statement consistency and mutation/quota serialization require a separate proof; no contention was measured.

`presence` is a small heartbeat write (`last_seen/avatar/activity_game`) returning `{}`. `hub` returns profile/friend/room/invitation/conversation metadata, not full archives or full chat history. Its superseded basic-friends aggregate is the bounded source-only SQL candidate above. DM/group reads cap each fresh page at80 and separately include requested known updates; old bodies are omitted for incremental known updates. Active invitation unions are deliberate, so the entire response is not claimed to be hard-capped at80. Pair/group indexes and current recipient/membership/history boundaries remain necessary.

Signaling's known-connected IDs suppress repeated SDP payloads. Per-peer `authorize` still checks membership and renews its real TTL; host poll also renews host liveness. These distinct capabilities are not equivalent duplicate calls. The account-sync wrapper retains its32-request/64KiB bounds, read allowlist and per-section error isolation. These are source observations, not current production/RPC timings or query-plan measurements.

History's catalogue-wide header lookup is a source-confirmed candidate for a single-header accessor. However, its first `progress` computes the presented/unread boundary and the second fresh `progress` plans missing frame requests after asynchronous work. Concurrent pushes can fill holes between them. Blindly reusing the old plan could send redundant history requests; a correct future change must combine/return the actual plan while preserving cursor and current-owner guards. No local change is justified by measured cost in this audit.

Presence's repeated encoding uses one explicitly public projection (no resume tokens, private hands or full Session). Sharing an immutable encoded string within that publication is possible; distinct authorized peer sends are required. This is a bounded CPU candidate, not redundant network traffic. Subscriber and retained-presence object copies remain intentional mutation-isolation boundaries. No new history/presence optimization, protocol or benchmark is included.

## Necessary work deliberately retained

- `AccountSyncService`: identical in-flight reads coalesce and independent sections share one aggregate request. Clones isolate cache/flight consumers; only Push config has a10s retained cache. Search results are not cached. Removing listener/consumer copies without an immutable API would break mutation isolation. Existing account-sync tests exercise dedupe, partial errors, account generations and incremental cursors.
- Supabase adapter: credentials/session check precedes RPC, aggregate uses a read allowlist, mutations/file get/put are not silently batched or cached. Request JSON serialization is the network boundary. Server aggregate caps requests32 and request JSON64KiB; no broad SQL optimization is being claimed.
- Cloud list responses explicitly project metadata and **exclude stored files**. File content is fetched only through get or supplied for put. A full portable archive/hash is required for independent backup, compatibility verification and conflict safety; it is not a public RTC payload.
- Cloud signaling: host poll already omits known connected SDP and supplies authenticated identity. Periodic authorize refresh also renews actual membership TTL and closes revoked capabilities; it is not equivalent to an unnecessary duplicate API call. Poll timing and exact wire shape remain unchanged.
- Online connect and recovery: duplicate connect joins share a flight; obsolete attempts are fenced. Recovery `check()` has one flight, hidden-tab suppression and explicit close cleanup. Its current projected snapshot reconciles a potentially missed update; replacing it with an unproven heartbeat would change recovery guarantees.
- WebRTC transport: messages are parsed once, then independent subscriber copies preserve consumer isolation and a separate retained public presence copy. Existing test mutates one received presence and verifies future subscribers are not poisoned. Authorized audience projections and late terminal-frame ordering must remain intact.
- Host journal: creation stores the private initial Session, later commits use the existing journal/event delta and durable receipt before ACK. Recovery validates missing/duplicate receipts. Client history uses an explicit projected allowlist and pooled replay events; no resume/authority tokens enter its frames. These copies are ownership/privacy/rollback boundaries, not removable merely because stringify/clone appears in source.
