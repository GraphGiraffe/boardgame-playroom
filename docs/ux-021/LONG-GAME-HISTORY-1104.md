# Рост затрат в длинной партии и выход из истории · 04.11

Запись экрана: Лудо, раунд 29, ход 113. По одной видеозаписи нельзя установить утечку памяти или длительность JS-задач телефона.

Исправлено:
- Engine больше не делает глубокую копию накопленных канонических событий на каждый ход: используются только принадлежащие ModelValues проверенные и глубоко замороженные снимки. Mutable внешние события по-прежнему отделяются копией, неструктурированные legacy-события сохраняют прежнюю mutable-копию.
- Events.project повторно использует уже проверенную immutable-проекцию события, раздельно по зрителю и количеству игроков. Ключи WeakMap не удерживают недостижимые журналы; сырые внешние объекты не считаются доверенными даже после shallow freeze. Переведённые тексты, имена игроков и игровые сцены не кешируются.
- Звуковые подсказки отбрасывают события до своего курсора перед проекцией, а не после обработки всей истории.
- В заголовке истории доступна непосредственная кнопка «Вернуться к партии» / «Закрыть историю», через существующий history-close и восстановление источника. Для сетевого экрана используется тот же общий компонент.

## Память и длительности

Chromium CDP, та же история500 действий,20 открытий/закрытий из библиотеки, reduced-motion и принудительный GC перед каждой точкой. JS heap:30.772МБ перед циклами,31.475 после5,31.660 после10,31.690 после15,31.711 после20. После первого цикла DOM сохраняет5329узлов и293обработчика. На этом сценарии рост замедляется к плато; линейное удержание DOM/обработчиков не обнаружено. Это не доказывает отсутствие утечек при длительной живой игре, звуке, полной анимации или на физическом телефоне. Память истории закономерно растёт с числом сохранённых действий; сокращение этого объёма не должно удалять ходы.

Параметры duration/settle/botDelay заданы четырьмя постоянными preset; длина партии их не увеличивает. В очереди feedback учитываются только события после cursor. Проверки game-flow17/17 подтвердили отмену/завершение таймеров и идемпотентное завершение плана; длительное реальное проигрывание анимаций телефона отдельно не измерялось.

Live PWA: первая попытка не загрузила страницу из-за net::ERR_CERT_VERIFIER_CHANGED; это не green. Свежий процесс без изменения сертификатов/сети прошёл6 состояний загрузки/офлайн. Исходный неуспешный отчёт сохранён рядом с live-pwa-retry.

## Две записи одной партии: 11:26 и 11:30

Первый клип41.17с: раунды3–6, ходы9–23. Второй11.73с: раунд24, ходы93–94. У второго клипа есть дополнительный бросок после шестёрки. Поэтому отношение количества ходов к длительности клипа не измеряет быстродействие приложения.

Просмотр последовательных кадров второго клипа: примерно1с — показ выпавших2/6; около2с виден контакт с фишкой; около3с показан доступный маршрут; около5с виден контакт с кубиком6, следом начинается перемещение. OCR с шагом250мс фиксирует описание перемещения около5.25с, следующего —6.25с, повторного броска —7.5с, последнего перемещения —10с, броска следующего бота —11.25с. Начало клипа пришлось на обновление предыдущего действия, поэтому OCR первого полусекундного кадра и исходный кадр могут иметь разные описания. Это приблизительные отметки видео, не JS input latency и не профиль main thread. Из них нельзя считать весь промежуток между броском и перемещением вычислительным зависанием.

Записи имеют переменные интервалы кадров, включая длинные интервалы на статических сценах. Средний FPS файла и разрывы PTS сами по себе не доказывают падения FPS интерфейса: записывающее приложение может пропускать неизменившиеся кадры. Версию запущенного приложения и свободную RAM из этих записей установить нельзя.

Дополнительный matched опыт памяти, отдельные Node-процессы с --expose-gc: исходные engine/events из проверенного sourceZIP перед исправлением против текущих, остальные модули одинаковые; Лудо seed17,4бота,2кубика.
