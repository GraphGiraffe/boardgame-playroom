# ХОД / Playroom — план единого web-приложения

**Статус:** актуальный план реализации после требований 7 октября 2026 года.  
**Рабочая ветка:** `feature/unified-lan-host`, основана на `feature/phone-pc-preview`.  
**Область:** в первую очередь `boardgame-playroom`; `boardgame-playroom-paks` меняется только там, где нужен однократный переход на стабильный документированный SDK.

## 1. Цель

Сделать **одно web-приложение «ХОД»** для ПК, телефона и планшета. Пользователь видит одну и ту же библиотеку, настройку режима, лобби, игру, историю и сохранения. Отдельные страницы `dev/*` остаются только тестовыми стендами.

Для сетевой партии на ПК организатора запускается хостовая часть той же поставки. Она раздаёт эту же web-сборку, владеет комнатами и авторитетной игровой сессией. Браузер на этом ПК — обычный клиент приложения с ролью **Игрок** или **Стол**. Телефоны и другие ПК открывают тот же интерфейс в браузере.

Локальные режимы **с ботами** и **hot seat** должны работать без запуска LAN-хоста.

## 2. Неподвижные архитектурные инварианты

1. Игровые правила исполняются одной `SessionAuthority`; transport и UI не меняют правила игры.
2. Пак не знает про IP, WebSocket, PIN, комнату, reconnect, системную историю, сортировку библиотеки или кнопку «Скрыть поле».
3. Основное приложение не содержит игровых веток вида `if (game === 'uno')`.
4. Пак содержит правила, состояние, видимость, игровую геометрию, бот-стратегию, изображения и специфические звуки.
5. Приложение содержит shell, layout, input, комнаты, сеть, persistence, историю, replay, reconnect, общий scheduler ботов и библиотеку.
6. Опубликованная версия пака неизменяема. Старая партия фиксирует точную версию и продолжает использовать её.
7. Новые возможности SDK по умолчанию аддитивны и optional. Изменение сети или меню не требует новой версии всех игр.
8. Для несовместимого будущего SDK используется новая версия контракта и legacy-адаптер, а не скрытая массовая поломка паков.
9. Сетевой клиент получает только разрешённую проекцию. Полный `Session`, RNG и чужие закрытые данные не передаются.
10. Один и тот же `GameShell` используется для локального и сетевого клиента; отличаются transport, viewer и полномочия, но не пользовательский продукт.

## 3. Четыре режима одного приложения

### 3.1. Игра с ботами

- Authority работает локально.
- Человек занимает своё место, остальные — `bot`.
- Стратегию хода предоставляет пак, scheduler и проверку результата — приложение.
- Старые сохранения и replay продолжают работать.

### 3.2. Hot seat

- Одна локальная партия, несколько человеческих мест.
- При передаче устройства очищаются чужие выборы, tooltip, осмотр, диалоги и личная история.
- Реакции вне очереди не сводятся к условию `actor === state.turn`.

### 3.3. Сеть: хост — Игрок

- Создатель комнаты занимает одно игровое место.
- Фактическое число участников определяется готовыми игроками в лобби перед стартом.
- Свободные места не заполняются фиктивными игроками и пока не заполняются ботами автоматически.
- Команды хоста проходят тот же `SessionClient → transport → authority`, что и команды удалённого игрока.

### 3.4. Сеть: хост — Стол

- Создатель комнаты не занимает игровое место.
- Устройство показывает публичное поле и публичные показатели, но не личные руки.
- Все игровые решения выполняются с устройств игроков.
- Организатор при желании может войти отдельным игроком с телефона.

## 4. Одна оболочка и один маршрут пользователя

Целевой путь:

```text
Библиотека
  → карточка игры
  → выбор режима
      ├─ Боты
      ├─ Hot seat
      ├─ Сеть · Игрок
      └─ Сеть · Стол
  → настройка игры
  → лобби (только сеть)
  → GameShell
  → история / завершение
```

Новые пользовательские сетевые страницы рядом с `app/app.js` не создаются. Экспериментальный `app/shared-views.js` используется как источник уже проверенной клиентской логики, затем его возможности переносятся в общий `GameShell`.

## 5. Граница стабильного SDK паков

### 5.1. Что уже можно переиспользовать

- `SessionAuthority`, `core/protocol.js`, `SessionClient`;
- `PlayroomViews.register(..., {surfaces})`;
- `H.art({main, compact, width, height})`;
- проекции `TabletopCore.project`;
- текущий installer/activation/rollback точной версии пака;
- `rules.min` / `rules.max` как базовые ограничения состава.

### 5.2. Что добавить аддитивно

Предлагаемые optional-возможности:

- семантические области сцены: `board`, `players`, `hand`, `status`, `actions`;
- стабильные semantic target ID для выбора цели;
- optional `playerCounts`, если игра допускает не все значения между `min` и `max`;
- optional маркеры истории: `turnId`, `cycleId`, `roundId` / `phaseId`;
- optional capabilities для `table`, `player`, `hideBoard`, специальных реакций и паузы при отключении.

Старый combined-renderer продолжает работать локально без изменений. Отсутствующая новая capability означает только отсутствие соответствующей новой функции, а не отказ запуска старой игры.

### 5.3. Правило стабилизации

До массовой адаптации пяти игр новый контракт доказывается на:

1. `examples/private-counter` — отсутствие карточных допущений и проверка приватности;
2. UNO — руки, реакции вне очереди, выбор цвета/цели, table/player;
3. одном не карточном паке — проверка board/targets.

После этого контракт фиксируется документом и regression-fixtures старых опубликованных `.playroom-pack.json`.

## 6. HostRuntime: часть приложения, не второй продукт

Из `dev/serve-preview.cjs` выделяется поддерживаемый runtime основного приложения.

Ориентировочные модули:

```text
host/
  runtime.cjs
  http-server.cjs
  room-service.cjs
  session-store.cjs
  host-identity.cjs
  pack-repository.cjs
```

Имена можно уточнить по фактическому коду, но границы ответственности сохраняются.

HostRuntime:

- раздаёт **тот же** `index.html`/web bundle;
- предоставляет API комнаты и сессии;
- владеет `SessionAuthority`;
- хранит сетевые партии и command receipts;
- обслуживает точные view-ресурсы установленного пака;
- позже запускает сетевых ботов;
- не содержит правил UNO/домино/шашек;
- не раздаёт рабочий каталог, БД, секреты или полный export сессии.

## 7. Комнаты, короткий номер и LAN

### 7.1. Внутренняя идентичность

- `hostId` — устойчивая идентичность установки хоста;
- `roomId` — длинный уникальный ID комнаты;
- `sessionId` — ID конкретной партии;
- `participantId` — участник комнаты;
- `seatId` — место в партии;
- `connectionId` — временное соединение;
- `authorityEpoch` — экземпляр исполнителя.

IP, nickname, socket ID и короткий номер не являются идентичностью игрока.

### 7.2. `#0123`

Короткий код — строка ровно из четырёх цифр с ведущими нулями. Он уникален среди активных комнат **конкретного HostRuntime**, а не глобально во всей сети.

Надёжный первый путь подключения:

1. открыть публичную ссылку/QR хоста либо выбрать его из «Недавних хостов»;
2. увидеть комнаты этого хоста или ввести `#0123`;
3. войти в комнату.

Это сохраняет отсутствие отдельного RoomHub.

В обычном браузере нельзя надёжно разрешить неизвестный `#0123` во всей произвольной подсети без начального адреса или дополнительного discovery-механизма. Поэтому первая версия не делает скрытый subnet-scan и не вводит внешний каталог. Позднее можно добавить optional discovery, не меняя паковый SDK.

### 7.3. «Поиск комнат в локальной сети»

Первая реализация трактует это как:

- текущий открытый HostRuntime;
- сохранённые/недавние LAN-хосты;
- параллельная проверка их доступности и списка комнат;
- редактирование изменившегося endpoint.

Автоматическое обнаружение полностью неизвестных хостов — отдельная platform-функция. Если для неё будет выбран mDNS/native helper, она принадлежит HostRuntime/launcher, а не паку.

## 8. Лобби и динамический состав

Комната проходит фазы:

```text
lobby → starting → playing → finished → closed
```

В лобби видны:

- игра и точная версия;
- правила/вариант;
- роль организатора: Игрок или Стол;
- участники, места, ready и connection-state;
- публичный `#NNNN`;
- доступ: открытая комната или PIN.

Правила:

- фактическое число игроков фиксируется при старте;
- допустимость проверяется по паку;
- изменение состава/правил/пак-версии сбрасывает ready и увеличивает `lobbyRevision`;
- двойной старт и гонка за последнее место сериализуются;
- после старта отключение не удаляет место;
- новый человек не занимает чужое место в середине партии;
- сетевые боты пока только резервируются архитектурой как `controller: human|bot`.

## 9. Доступ, PIN и возврат

- Комната открытая либо с автоматически созданным PIN из **6 цифр**, включая ведущие нули.
- PIN — только первичный допуск, не ключ игрока и не admin-secret.
- После допуска выдаётся длинный `resumeSecret` конкретного participant/seat.
- Публичная ссылка и QR не содержат `resumeSecret` или admin-secret.
- Вторая вкладка не создаёт второго игрока: одна управляющая lease на место, остальные либо read-only, либо требуют явного перехвата.
- Неверный PIN ограничивается rate-limit; секреты не пишутся в лог.

## 10. Транспорт

### Шаг 1

Сохранить HTTP snapshot/command API как проверяемую совместимую основу, но обслуживать её из HostRuntime и через общий web-shell.

### Шаг 2

Добавить `WebSocketTransport` за существующим интерфейсом transport:

- snapshot + подписка без polling;
- упорядоченные commit-сообщения;
- reconnect/backoff;
- backpressure/ограниченная очередь;
- fallback на явный refresh snapshot.

Пак не знает, какой transport используется.

HTTP/WS первой LAN-preview предназначен только для доверенной сети. PIN не является шифрованием. HTTPS/WSS и модель доверия хосту — отдельный security-gate перед стабильным выпуском.

## 11. Долговечность и exactly-once effect

`SessionStore` находится в HostRuntime и транзакционно хранит:

- метаданные room/session;
- точный game + pack version + digest;
- состояние/checkpoint;
- подтверждённые commands/events;
- fingerprint команды;
- receipt по `commandId`;
- participant/seat bindings;
- history cursor/index metadata.

Порядок команды:

1. проверить connection и seat;
2. проверить session/protocol;
3. найти прежний `commandId`;
4. только для новой команды проверить `expectedRevision`;
5. детерминированно вычислить переход;
6. транзакционно сохранить состояние + журнал + receipt;
7. после commit опубликовать новую ревизию и ACK.

Потеря ACK после пункта 6 не исполняет ход повторно. После restart прежний command ID разрешается по журналу. При ошибке диска окончательный успех не возвращается.

Конкретный backend выбирается отдельно, но должен поддерживать атомарную запись и блокировку единственного владельца сессии.

## 12. Reconnect

Клиент хранит:

- `hostId` и последний endpoint;
- `roomId/sessionId`;
- `participantId/seatId`;
- `resumeSecret`;
- неподтверждённый command envelope;
- курсоры истории.

После reconnect сначала выполняется handshake/resume, затем актуальный snapshot с согласованной границей дальнейших commits. Старый snapshot не откатывает UI. Смена authority epoch не стирает receipts.

Потеря связи не означает выход, пас, штраф или автоматическую замену ботом.

## 13. История и пропущенное

Нужно различать:

- **event** — событие правил;
- **action/command** — подтверждённое действие;
- **turn** — смысловой ход, если его разметил пак;
- **cycle/round** — только если правила дают такую семантику.

Клиент хранит три независимых показателя:

- `receivedThrough`;
- `presentedThrough`;
- `reviewed` интервалы.

После отсутствия приложение показывает рядом с историей, например: **«За время отсутствия произошло 5 действий. Посмотреть»**.

Быстрые переходы:

- предыдущее/следующее действие;
- моё действие;
- мой ход — если поддерживается;
- пропущенный диапазон;
- круг/раунд — если поддерживается;
- к текущей партии.

UNO не получает искусственные «круги» по формуле из количества действий.

История загружается страницами, а live-состояние продолжает обновляться. Исторический кадр read-only. Публичный Стол получает только публичную историю, игрок — историю своей проекции.

## 14. GameShell и режим Стола

Целевой `GameShell` получает `SessionClient` и локальный UI-state. Он не получает полный `Session`.

Для обычного игрока по умолчанию показываются:

- поле;
- своя рука;
- остальные игроки и их разрешённые руки;
- status;
- actions;
- история;
- connection state.

Для Стола используются публичная проекция и layout без личной руки.

### «Скрыть поле»

У игрока есть быстрая локальная кнопка **«Скрыть поле / Показать поле»**.

Она:

- не является игровой командой;
- не влияет на других клиентов;
- не скрывает руку, оппонентов, status, actions и историю;
- сохраняется на устройстве;
- при необходимости временно раскрывает board либо показывает semantic targets для выбора.

Для legacy-пака без regions функция может быть недоступна, но локальный combined-режим не ломается.

## 15. Сортировка и адаптивная библиотека

Базовые сортировки:

- по названию;
- недавно запущенные;
- недавно установленные.

Позднее можно добавить избранное.

Принципы:

- одна карточка на game ID, даже если установлено несколько версий;
- сортировка стабильная;
- выбор сохраняется;
- карточка не прыгает под пальцем при обновлении статистики;
- responsive grid выбирает число колонок по ширине контейнера;
- задаётся минимальная читаемая ширина и максимальное растяжение;
- 1/5/30/100 игр проверяются на телефоне, планшете и desktop;
- cover приходит из пака, layout/text/focus — из приложения.

## 16. Сетевые боты — следующий блок

Сейчас заранее закладывается `SeatController: human|bot`, но UI добавления ботов не входит в первую LAN-приёмку.

Позже:

- организатор добавляет/удаляет ботов в лобби;
- стратегия остаётся в паке;
- scheduler и исполнение работают в HostRuntime;
- bot action проходит ту же authority/receipt очередь;
- reconnect не запускает второй bot-loop;
- human↔bot replacement требует отдельной политики.

## 17. Последовательность реализации

### P0 — этот документ и фиксация архитектуры

- зафиксировать единый web-app, встроенный HostRuntime и границу паков;
- отметить зависимость ветки от `feature/phone-pc-preview`;
- актуализировать ROADMAP.

**Готово, когда:** в репозитории нет противоречащего актуального плана без пометки о его историческом статусе.

### P1 — общий GameShell и ModeController

- свести `app/app.js` и полезную логику `app/shared-views.js`;
- перевести локальные действия на `SessionClient + local transport`;
- сохранить ботов и hot seat;
- не менять first-party packs без необходимости.

**Приёмка:** прежние локальные режимы и старые saves проходят regression; private-counter не получает секреты через shell.

### P2 — продуктовый HostRuntime и единая web-сборка

- вынести серверную основу из `dev/serve-preview.cjs`;
- раздавать основной `index.html`;
- добавить host identity, ограниченные routes и pack view delivery;
- открывать то же приложение на ПК хоста и телефоне.

**Приёмка:** ПК одновременно хостит и использует приложение; телефон открывает тот же UI по LAN; `dev/view-client.html` не является продуктовым путём.

### P3 — RoomService, `#NNNN`, PIN и лобби

- Room/Participant/Seat/Connection;
- Игрок/Стол;
- динамический состав;
- ready/lobbyRevision;
- короткий host-scoped code;
- recent hosts;
- resumeSecret.

**Приёмка:** хост-игрок + 2 клиента стартуют втроём; хост-стол + 2 клиента — вдвоём; гонки последнего места и двойной старт безопасны.

### P4 — SessionStore и восстановление

- atomic commit;
- receipts;
- restart recovery;
- one-owner lease;
- pending-command resolution.

**Приёмка:** потеря ACK, refresh, краткий Wi-Fi-разрыв и restart не дублируют и не теряют подтверждённый ход.

### P5 — WebSocket transport и синхронизация

- push snapshots/commits;
- reconnect/backoff;
- bounded queues;
- отсутствие повторных эффектов.

**Приёмка:** polling больше не нужен для live-игры, но transport остаётся заменяемым.

### P6 — HistoryService

- page API;
- actor/turn/cycle indexes;
- missed intervals;
- HistoryPanel;
- live/replay separation.

**Приёмка:** длинная история не блокирует live, приватность прошлого сохраняется, пропущенное не отмечается просмотренным само по себе.

### P7 — regions, скрытие поля и библиотека

- regions/targets;
- полноценный player/table layout;
- hide/show board;
- responsive library grid + sort.

**Приёмка:** игрок выполняет все действия со своего экрана; 1–100 карточек библиотеки удобны без изменений паков.

### P8 — однократная адаптация first-party паков

Только после фиксации SDK.

- UNO: реакции, status, player/table;
- Домино: board targets/end/orientation;
- Дурак: attack/defense targets;
- Шашки: cell targets/continued capture;
- Змеи и лестницы: board/status/optional cycle metadata.

Новая версия выпускается только у действительно изменившегося пака. Старые опубликованные артефакты остаются regression-fixtures.

### P9 — launcher, security gate и физическая приёмка

- runtime в удобной host-поставке;
- занятый порт/Firewall/LAN errors;
- выбранный HTTPS/WSS path;
- Android Chrome, iOS Safari, desktop Chromium/Firefox;
- sleep/background/orientation/zoom.

Стабильный релиз только после отдельного разрешения.

### P10 — сетевые боты

Отдельный следующий функциональный этап после устойчивых комнат/reconnect/history.

## 18. Тестовый минимум каждой итерации

Сохраняются два уровня:

1. независимый app/core набор;
2. совместный набор с зафиксированными pack artifacts.

Обязательные регрессии:

- legacy pack без новых optional capabilities;
- старая сохранённая партия;
- install/activate/rollback;
- hidden fields в JSON/DOM/aria/history/effects;
- duplicate command и duplicate ACK;
- stale snapshot/revision;
- last-seat race;
- double start;
- invalid PIN/resume;
- restart до/после commit;
- две управляющие вкладки одного seat;
- 320×640, 390×740, 640×320, 740×390, 1366×768, 200% zoom;
- руки 1/7/14/30/35;
- orientation во время выбора;
- touch/drag/swipe;
- библиотека 1/5/30/100 игр.

Физическая проверка устройства фиксируется отдельно и не подменяется viewport-эмуляцией.

## 19. Что не входит в ближайшую реализацию

- глобальный интернет matchmaking;
- аккаунты;
- TURN/WebRTC как обязательный transport;
- автоматическая миграция хоста;
- произвольный новый игрок после старта;
- сторонний облачный RoomHub;
- полная sandbox-модель недоверенного pack JS;
- 3D;
- сетевые боты до P10;
- автоматическое обнаружение неизвестного host только по `#0123`.

## 20. Ближайший кодовый шаг

После принятия этого плана первая кодовая итерация должна быть **P1 + начало P2**:

1. общий `GameShell` поверх `SessionClient`;
2. единый ModeController для bots/hot-seat/network;
3. продуктовый HostRuntime, который отдаёт основной web-app вместо отдельного `view-client.html`;
4. минимальный RoomService API без изменения паков;
5. regression старых локальных режимов.

Только после этого добавляются PIN, `#NNNN`, persistence и расширенная history. Это уменьшает вероятность ещё раз построить отдельный сетевой UI, который затем придётся объединять с основным приложением.
