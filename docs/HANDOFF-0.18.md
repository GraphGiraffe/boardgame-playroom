## 4. Что сделано в 0.18 до RC4

- Все 12 игр перенесены на engineApi 3: чистые детерминированные domain, отдельные presentation и locale JSON, Web view. Старые **engineApi 1/2** больше не загружаются; предусмотрено полное обновление с сохранением возможности экспорта исходных данных.
- Общие Session/history/codec/events/CommandProcessor, durable authority/ACK/retry, application services комнат/подключения/recovery/истории выделены из Web-кода. Платформенные порты остаются отдельно.
- `shared/pack_compiler.py` паков — канонический compiler; приложение использует закреплённую SHA копию `tooling/pack_compiler.py` и lock. Ассеты приложения вендорятся с provenance из паков.
- Общие SVG круглый диск, фишки/счётчики/медали/первый игрок/команды, веер/стопка, кубики, карты, домино, шашки, баблы, таблица Ятзи и стандартные звуки. Лудо и Змеи используют одну фишку; старое принятое поле Лудо сохранено, финишные фишки раскладываются треугольником. Масштабирование из общего artboard, без текстовых смещений при изменении размера.
- Локальные светлая/тёмная неизменяемые темы и пользовательские сохранённые пресеты, редактор в главном меню, переключение в партии. Палитры и material/skin hooks не меняют правила и вид других клиентов. В тёмной теме обычные игральные карты сохраняют светлое лицо; подложки используют системную палитру.
- Стол = Зритель плюс возможность совершать разрешённые публичные действия. Viewer и actor разделены; приватность фильтруется до UI/звука/истории. Руки видны рубашками или лицами при открытом режиме; в Морском бое скрыты оба флота. Приватные действия выполняются с личных устройств.
- Скрыть поле можно только сетевому игроку при подключённом Столе, с личными руками/карточками на освобождённом месте. Нельзя в hotseat/локальной игре/истории/обычном зрителе/без Стола. Пауза всегда в быстром доступе, история уступает место переключателю поля; команды продублированы в настройках.
- Разделены действие, ход и раунд. История: `<`/`>` по ходам, `≪`/`≫` по раундам; метки точками и черточками внутри линии. Подготовка Морского боя не считается игровыми ходами. История разрешает безопасные controls просмотра (например, выбор поля/автопоказ), но не игровые действия.
- Применимые режимы завершения/последний круг/до последнего и пределы раундов объявляются паком; UNO не объявляет раунд. Краткие справки отдельных настроек и общие правила структурированы.
- Общая очередь семантических звуков/уведомлений skip/pass/draw/discard/take/reverse и крупного показа подходящих **публичных** ходов. Один основной звук на действие. UNO +2/+4 и reverse в дуэли имеют skip feedback. Крупный показ центрирован по видимой зоне поля, с длительностями по настройке скорости и без растягивания документа.
- RC2/RC3 устранили замечания про drag, тему, размеры фишек, границы выделений, scroll, мигание flip, доступность UNO и просмотр разных полей. Отчёты содержат точные области проверок; не объявлять все физические устройства проверенными.

## 5. Что добавляет RC4

### Главное меню и списки

- Карточки всех 12 игр всегда квадратные, на телефоне две колонки; пропорции внутренних элементов масштабируются от ширины карточки.
- Сверху круглый тип игры, число игроков, избранное. Play убран: нажимается вся карточка. Механики отдельной компактной строкой, арт по центру своей области, текст не перекрывает рисунок, название/описание занимают фиксированные зоны.
- Избранное доступно и при редактировании. Перетаскивается карточка целиком, кнопки вверх/вниз поверх подписей не меняют геометрию. Звезда центрирована и согласована по размеру.
- Одинаковый `packRow` для «Паки игр» и «Сменить игру»: квадратный маленький арт на том же цвете, что в хабе, имя и ID/версия; без «выбранная версия». В выборе игры нет управления порядком/удалением/видимостью/избранным.
- Заголовки окон слева. Быстрые кнопки настроек одной строкой, никнейм ниже, без дублирующих больших кнопок темы/правил. Верхняя панель лобби без лишних темы/справки; они доступны в настройках.
- Иконка поля облегчена: наклонённая сетка без обводки. Иконка кубиков — две кости, одна под наклоном. Ятзи — красный невысокий стаканчик с вылетающими костями, UNO без галочки, Дурак с двумя шестёрками.

### Компоновка партии

Пак задаёт `layout.focus: hands|field|balanced`, `layout.seats` и `layout.duplicateSelf`. Общая адаптивная реализация принадлежит приложению. Круговая рассадка по умолчанию, ряд — локальная настройка. Для двух игроков без особых якорей остаётся обычная раскладка. Приоритет рук у Акулины/Рыбы. В Лудо карточки около баз и компактная копия собственной карточки у своей базы. Смена layout не меняет очередность, viewer или скрытую информацию.

### Персонажи и аватары

- 8 форм: месяц, треугольник, квадрат, круг, звезда, прямоугольник, ромб, шестиугольник. 6 цветов: красный, оранжевый, жёлтый, зелёный, синий, фиолетовый. Всего **48**.
- Фиксированные разные позы/лица и аксессуары: месяц с ночным колпаком, треугольник с праздничным колпаком, квадрат в круглых очках, круг с бабочкой, звезда с короной, прямоугольник в тёмных очках, ромб с шарфом, шестиугольник в кепке.
- Отдельные пакеты `shared/asset-packs/characters` и `cartoon-deck`. PNG 512×512 RGBA — канонические, WebP 256×256 — runtime. Мультяшные растровые иллюстрации — согласованное исключение из SVG игровых компонентов.
- Принятые концепты в `playroom-paks/docs/design/pexeso-characters/`; прошлые варианты персонажей и Ятзи сохранены. **Простые геометрические карточки удалены** по прямому указанию владельца.
- Выбор аватара на первом вводе имени и слева от ввода имени в настройках. 6 столбцов, буква имени — 49-я квадратная ячейка того же размера, без видимой подписи. По умолчанию первая буква. В партии остаётся видимый цветной ободок места игрока; изображение вписано/обрезано внутренним скруглённым квадратом.
- Только allowlist ID пресетов, без внешних URL. Кастомная загрузка и будущая кнопка с пунктирным плюсиком **пока не реализуются**.
- Профиль: `platform/web/identity-store.js`; изображения/валидация: `core/avatars.js`, сгенерированный offline `core/character-assets.js`; picker: `app/avatar-picker.js`. Комнаты/сеть/сессии/результаты передают avatar ID.

### Пексесо и самостоятельные ассеты

- По умолчанию мультяшная колода, точная пара = персонаж + цвет; 48 пар в полном режиме / 96 карт. Режимы easy/medium/hard берут 8/12/18 пар. Игральные колоды 36/52/54 сохранены.
- Пак `pexeso` stateVersion 3, новая RC версия, старые опубликованные пакеты неизменны. Обложка — красный круг и жёлтый месяц.

- Сборка паков создаёт отдельные ZIP `playroom-assets-characters-0.1.0.zip` и `playroom-assets-cartoon-deck-0.1.0.zip`, кроме общей коллекции/общего архива ассетов. Cartoon-deck зависит от characters, не содержит второй независимой копии иллюстраций. Это source/build dependency и отдельный download; самостоятельного UI импорта произвольных asset ZIP сейчас нет.

Все HTML JS/CSS entrypoints теперь автоматически входят в precache CORE, а не только в INTEGRITY; версия cache берётся builder из package.json. Это отдельный immutable app release; коллекция и ассеты остаются RC4. Для следующих новых entrypoints проверять и CORE, и integrity.

### Git, gh и сеть

- На момент работы `gh` имел недействительный токен в hosts.yml при работающем git HTTPS. Пользователь затем исправил `gh auth status`; не считать это постоянной неисправностью. Проверять отдельно `gh api user` и git push/remote.

В этом сеансе временный helper `/tmp/playroom-gh.py` делал именно это; сам файл не содержит credential, но не является обязательной частью репозитория.
- В сеансе запросы через существующий SOCKS-прокси иногда давали connection reset; для отдельных GitHub процессов работал прямой маршрут с `env -u HTTP_PROXY -u HTTPS_PROXY -u ALL_PROXY -u http_proxy -u https_proxy -u all_proxy ...`. Не менять системный прокси, профили, TUN, работающие сервисы или соединение пользователя.
- При 504 на merge **не повторять мутацию вслепую**: прочитать `gh pr view --json state,mergeCommit`. Оба RC4 PR были подтверждены MERGED после временной ошибки ответа. Проверять remote SHA, не только локальный git log.
- Сохранять многострочные PR/release descriptions в файле и передавать `--body-file`/`--notes-file`. Не подставлять тексты через shell command substitution и не использовать JSON.stringify как shell quoting.
- Готовность PR/push не запускает тесты автоматически; Actions запускаются вручную по выбранной операции. Проверить required checks на фактическом HEAD, не предполагать, что старый gate относится к новому коммиту. `main` не нужен для RC: теги prerelease закрепляются на проверенном dev SHA.

### Разные версии контрактов — не смешивать

Текущие правила `engineApi=3`; Web view и Elements scene остаются `viewApi/api=2`, чистый model contractVersion=1, сеть protocolVersion=2, игровой JSON formatVersion=1, asset-pack formatVersion=1, профиль version=1 (avatar — добавочное поле). Число 2 само по себе не означает legacy. `stateVersion` индивидуален у каждой игры; Пексесо теперь 3. Не поднимать все эти номера одновременно и не удалять актуальный Web API 2 как «старый движок».

### Компиляция и ассеты

- Правила и Web ассеты игры менять в `playroom-paks/packs/<id>`. Приложение подключает их через `python3 build.py --prepare-dev --packs-dir ../playroom-paks/packs`; `packs`/`installed-packs.js`/`app/version.js` генерируются и игнорируются Git.
- Канонический compiler: packs `shared/pack_compiler.py`; app `tooling/pack_compiler.py` должен совпадать побайтно, digest в `tooling/compiler-lock.json` обновляется вместе с ним. Нельзя править только один builder.
- Общие ресурсы паков вендорятся в app по `core/shared-assets.json`/`core/component-assets.json` с digest. Некоторые vendored core файлы **намеренно коммитятся** для автономной сборки приложения. Не смешивать их с игнорируемыми сгенерированными previews/installed packs. В частности `core/character-assets.js` содержит offline каталог с data URI и не должен быть удалён как «случайный base64».
- Смена содержимого уже опубликованного ассета/пака требует новой версии. Новые самостоятельные ZIP ассетов включены в SHA256SUMS и Release. Импорт игровых JSON в приложении и импорт произвольных asset ZIP — разные возможности; последняя пока не сделана.
- При переиздании same-version build нельзя перезаписывать опубликованные Release файлы. Итоговый runtime/PWA должен соответствовать exact source SHA в release-info.json; поздний docs-only handoff commit может быть новее тега, но не меняет опубликованный runtime.

### Проверки и браузер

- `tests/blocks.cjs` — реестр: каждый `*.test.cjs` ровно в одном блоке, незарегистрированные/дубли отвергаются runner. Новый regression помещать в существующий подходящий файл либо регистрировать новый ровно один раз.
- `npm test` запускает всё. Для патча использовать `node scripts/codex/test.cjs case/...,block/subblock`, сначала `--list` при сомнении. Сквозные миграции могут обосновывать явный полный набор, но это не default.
- Проверять не только исходный view, но и compiled JSON/экспорт для сетевого клиента. У Пексесо legacy тесты стандартной колоды должны выбирать `deck:'52'`; default теперь cartoon. При проверке подделанного GameModel state валидатор бросает POSITION_INVALID, а не возвращает false.
- `scripts/codex/browser.cjs` ищет доступный Chrome и оборачивает Playwright. Обычно автозаполняет тестовый профиль; `playroomProfile:false` нужен для первого ввода имени. Для persistence предпочтителен `tests/browser-origin.cjs` с временным loopback HTTP origin, не file:// localStorage.
- Браузер в ограниченной среде может требовать отдельно разрешённого запуска. Если автоматическая проверка разрешения истекла по таймауту, это не доказательство запрета; допустим один повтор. Не выдавать непройденный/прерванный тест за зелёный.
- Фиксировать viewport, тему и состояние. Скриншоты сохранять в `tmp_files`, прикладывать в чат изображениями. Примеры RC4: `tmp_files/rc4-review/` и `tmp_files/rc2-presentation/`. Временные `/tmp/rc4-*.cjs` использовались для визуального согласования; это вспомогательные сеансовые сценарии, не обязательная часть проекта или замена зарегистрированным tests.

### Публикация/наблюдение

- App build с `--remote-catalog` даёт PWA, читающую защищённый каталог; standalone all-games HTML содержит выбранные source packs. Не подменять один тип артефакта другим при проверке.
- GitHub Release, публикация R2 и Pages deployment — три разных шага. Для нового канала R2 используется bootstrap; пустой channel выбирает production и недопустим для RC. App gateway preview требует `pack_channel`, не production deploy.
- Все workflow должны получать явный `checks`; публикация immutable артефактов — `none`. Это сознательный пропуск повторного запуска source tests, **не** пропуск SHA/build/protected smoke.
- Защищённый smoke ограничивает API запросы одним origin; временные transport errors и 404/5xx читающих GET повторяются ограниченно. Проверки пароля, доступа, bytes/SHA и offline не ослабляются; в диагностике только тип ошибки/путь, без cookies/password.
- В Pages используются прежний проект, private wrapper, Access/R2 binding и секреты Actions. Не копировать закрытый Worker/password/access kit в Git/Release/Markdown. Не создавать новый проект Pages ради ошибки распространения.
- Ожидать конкретный run ID, например `gh run watch ID --interval 30 --exit-status`; не запускать workflow повторно, пока не известен результат текущего. Если после загрузки smoke встретил временный 404, сначала проверить уже созданный deployment, не плодить новые uploads.
- При сбое smoke после upload не создавать новый preview вслепую. Для готового RC5 preview поддержан read-only gateway: `operation=preflight`, `checks=none`, `release=v0.18.0-rc.5`, `deployment=cc0f5728-375f-4e3a-94ef-3333571c9f68`, `pack_channel=0.18-rc.4`. Он сверяет commit с release, скачивает и проверяет PWA, выполняет полный smoke готового preview и online baseline production до/после; не вызывает upload/PATCH. Отчёт: `uploaded=false`, `productionUnchanged=true`.
- `release-info.json` сейчас создаётся выпускным шагом отдельно от build.py: exact app/packs SHA, версии, канал, выбор проверок. Его SHA добавляется в SHA256SUMS; не брать старый файл из переиспользованного output dir. Для нового кандидата выбирать отдельный свежий выходной каталог.
- Итоговый artifact `pages-deployment-report` содержит URL/commit/channel и `productionUnchanged`; перед финальным ответом сверить его и downloadable release SHA256. Стабильность production дополнительно подтверждается неизменными main SHA и production pointer. Фоновый мониторинг/планировщик без необходимости не добавлять.

### Новый чат

Не переносить всю старую историю и не форкать её: торможение связано именно с объёмом контекста. Достаточно START-NEXT-CHAT.md и этого документа. Создавать через штатный Codex CLI/app-server API; не писать SQLite/registry вручную и не останавливать текущий App/Remote ради создания чата. Отдельно проверить, что новый thread получил правильный cwd, начальное сообщение со ссылкой на preview и ответ; не объявлять появление в UI проверенным только по локальному thread ID.

Для автоматического создания нового интерактивного чата проверен штатный `codex app-server --listen stdio://`: `initialize` → `initialized` → `thread/start` с cwd контейнера → `thread/name/set` → `turn/start` с START-NEXT-CHAT → `thread/read` для подтверждения. Схемы текущей версии CLI доступны через `codex app-server generate-json-schema --out /tmp/...`. Прямой stdio сервер не перезапускает действующий daemon. `codex exec` не выбран: его source может не входить в стандартный список интерактивных чатов. Этот путь не требует ручной правки SQLite/проектов.

- Морской бой `0.2.0-rc.5`, stateVersion 4: каждый выстрел — ход, раунд после очередей обоих; setup не считается. Старые партии требуют свою прежнюю точную версию, immutable RC4 сохранён.
- При следующем кандидате брать новую версию/output dir. Опубликованные RC7 артефакты и SHA256SUMS не переписывать. Поздний docs-only commit не меняет runtime tag SHA. Production остаётся 0.17.6 / 0.6.5 и canonical `bddc9741-d208-42a8-adf6-ab8e8de655c9`.

## После RC7: рамки руки и строки игроков недавней партии

## После RC7: кубики, Ятзи и применимость рассадки

Крупный показ dice удерживается 500/800/1100/1500 мс (instant/fast/normal/slow), отдельно от принятых таймингов карт UNO. Причина задержки своих перебросов: `GameFlow.present` ждал минимальный бюджет card flip/reveal после уже закончившейся анимации кубиков. Теперь для новых projected roll/dice событий локально, по сети и в истории ввод разблокируется по фактическому завершению эффекта. Обычный переброс Ятзи остаётся анимацией кубиков на месте; крупный показ — при записи комбинации.
