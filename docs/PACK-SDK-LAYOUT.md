# SDK: зоны игрового экрана — первая итерация

Обязательный контракт переноса существующих игр: [совместимость с 0.21](SDK-COMPATIBILITY.md). Наличие общей сцены не означает завершённую визуальную приёмку.

Область применения: приложение **0.21.0** и коллекция **0.9.0**, engineApi 4 / viewApi 3 / protocol 3. Исторические этапы ниже поясняют совместимость; актуальное приложение доступно на [сайте](https://graphgiraffe.github.io/playroom-hod-test/).

Статус: **первая экспериментальная host-реализация и план миграции**, 5 ноября 2026. Начинается вместе с текущей унификацией интерфейса по комментариям Samsung S23. Этот документ не объявляет готовыми публичный API раскладки, миграцию всех игр или измеренную производительность телефона. План всего SDK: [PACK-SDK-LAYOUT.md](PACK-SDK-LAYOUT.md).

## Граница двух видов зон

`SceneModel.zones` описывает игровые области и разрешённые объекты: поле, руку, источник, владельца и количество. Эти данные принадлежат presentation пака после фильтрации по viewer. Экранные зоны определяют, **где** host показывает такое содержимое. У них другая ответственность: доступный прямоугольник, отступы, выравнивание, слои и переполнение. Экранная зона не создаёт объектов, команд или дополнительных прав.

Пак предоставляет авторизованное содержимое и семантические особенности игры. Движок выбирает стандартное расположение; пак не вычисляет ширины по числу игроков, не угадывает модель телефона и не копирует host CSS/обработчики resize. Режим истории использует тот же контракт и доступную для истории проекцию, сохраняя заголовок «История» и маршрут возврата.

## Что уже существует, а что требуется

| Основа в коде | Статус и граница |
|---|---|
| `SceneModel.zones/objects/interactions` | Действующий игровой контракт, описан в [COMPONENT-SDK](../../playroom-paks/docs/COMPONENT-SDK.md). Не заменяется экранными зонами. |
| `app/game-screen.js`, общие `.layout-field`, `.layout-participants`, `.layout-self`, `.layout-hand`, `.layout-actions` | Действующие host слоты и механизм раскладки. Названия классов — внутренние детали, а не новый публичный SDK. |
| `landscapeZones`, `placeSceneActions` | Host резервирует читаемые боковые зоны, затем отдаёт остаток полю. Измеренный список соперников занимает одну колонку, если помещается по высоте; руки показаны справа. Верхние панели и контур сцены используют фактические границы боковых зон. Перенос действий сохраняет существующий узел. |
| `geometryOwners`, региональные измерения и фиксированная геометрия | Действующая основа. Требует проверок сохранения геометрии/узлов при каждой миграции; не обещает отсутствие полного обхода во всех играх. |
| `alignInZone`, `zoneOutline`, `layout.overrides` | Первая экспериментальная реализация: выравнивание прямоугольника, скругление заданного контура и ограниченные пакетные переопределения зон. Полного публичного набора SDK ещё нет. |

Сохраняются `engineApi 4 / viewApi 3 / protocol 3`. Новое необязательное описание не должно менять правила, сетевой снимок или формат сохранения. Обязательные поля и смена API требуют отдельного решения о совместимости.

## Реальные экспериментальные точки входа

Экспорты `PlayroomGameScreen` (CommonJS: `app/game-screen.js`) принадлежат host; это пока не стабильный общий namespace пака:

- `landscapeZones(width, height, opponents, hasSelf=true, selfWidth=null, opponentMinimum=0, rosterFit=null)` возвращает `{opponents, field, self, columns}` в CSS px. Учитывает внутренние поля 12 px и два промежутка по 6 px; сначала резервирует минимум 144 px на карточку соперника и 240 px на локальную зону с рукой, затем ограничивает поле оставшимися шириной и высотой. `opponentMinimum` учитывает измеренные счётчики/руку. Если `rosterFit.height <= rosterFit.availableHeight`, используется одна колонка; иначе при достаточной ширине допускаются две. `selfWidth` сохраняет ширину локальной зоны при переходе в fullscreen. Функция сама не читает DOM/safe area.
- `alignInZone(zone, size, {inline='center', block='center', inset=0})` возвращает `{x,y,width,height}`. Обе оси принимают `start/center/end`; неверное имя даёт ошибку. Размер обрезается до доступного внутреннего прямоугольника независимо по осям. Это **не** вписывание с сохранением aspect ratio. Числовая валидация неконечных значений не является готовым контрактом.
- `zoneOutline(points, radius=12)` возвращает строку SVG path со скруглёнными углами. На вход нужен уже упорядоченный простой контур объединённой области: функция **не вычисляет объединение произвольных прямоугольников**. Валидация самопересечений/пустого контура пока не предоставлена.
- `core/ui.js` проверяет ограниченный объект `layout.overrides` и передаёт только известные параметры зон. Общий renderer пасьянсов объявляет `fieldColumns: 3` для боковых стопок; приложение рассчитывает размеры зон, renderer размещает собственные элементы. Произвольный CSS компоновки общей карточки не передаётся.

Эти возможности — начало SDK, не готовая замена остальных контрактов. Проверки текущего кандидата и незакрытые замечания: S23-COMMENTS-1105.md. После стабилизации нужен запускаемый авторский пример на этих же экспортируемых модулях и контрактный валидатор расширений.

## Семантические экранные зоны

Имена ниже — словарь контракта, **не обещание существующих JS-экспортов**.

| Зона | Содержание и владелец |
|---|---|
| `header` | Обложка и название либо «История»; host. |
| `status` | Короткий ход/раунд/существенное событие под названием; host форматирует разрешённые данные. Без декоративного кружка и сообщений «партия началась». |
| `opponents` | Карточки остальных участников; host компонует авторизованные панели. |
| `board` | Поле/основная игровая область пака; host предоставляет прямоугольник, пак размещает объекты внутри него. |
| `quickActions` | Общие быстрые действия; host. Не смешиваются с игровыми действиями игрока. |
| `player` | Игровые действия, рука и подсказка текущего viewer; общий контейнер host. |
| `self` | Собственная карточка без дублирования; в обеих ориентациях снизу. |
| `overlay` | Чат, подсказки и drag preview; host. Не меняет размеры руки и карточек. |

Отсутствующая механика не требует фиктивной руки или игрока. Резерв стандартного профиля при этом стабилен: отсутствие содержимого само по себе не расширяет поле и не сдвигает остальные зоны. Для spectator/solo применяется явно выбранный профиль, а не скрытое исключение по game ID.

## Стандартное размещение

Это default **для всех игр**, а не профиль только Потасовки или карточных игр. Потасовка служит первой проверкой общей реализации. Исключения допускаются только для явно оговорённых раскладок ниже; наличие исторической паковой вёрстки само по себе не основание для исключения.

**Вертикально.** Компактная обложка/название и статус занимают две строки слева, общие быстрые действия — справа в той же полосе. Ниже оппоненты, поле, интерфейс viewer; собственная карточка закреплена внизу. Оппоненты занимают максимум три колонки. Число колонок меняет только содержимое выделенной зоны, а не размер всей сцены на каждом действии. Счётчики укладываются в общую высоту панели с симметричными отступами вокруг аватара.

**Горизонтально.** Host сначала резервирует читаемые боковые зоны, затем вписывает центральное квадратное поле в оставшиеся ширину и высоту. Если измеренный список оппонентов помещается по высоте, используется один столбец; иначе при достаточной ширине — два, а тесная зона прокручивается. У обычных карточек оппонентов рука располагается справа от аватара и счётчиков, сокращая высоту карточки. Компоновка выбирается при начальном размещении и смене viewport; игровые обновления сохраняют геометрию. Слева сверху — название/статус, справа сверху — общие быстрые действия; ширины и края этих панелей совпадают с фактическими боковыми зонами. Оппоненты по умолчанию выровнены сверху, собственная карточка — снизу. Игровые кнопки над группой собственной карточки и руки; рука рядом с карточкой без пустого промежутка. Явный профиль bottom-seats оставляет обе карточки Морского боя снизу; base anchors Лудо сохраняются. При меньшем числе участников не переносить свою карточку к середине.

Подложка объединяет игровое поле, панели участников и интерфейс viewer, исключая прямоугольники шапки и быстрых действий. Скругляются внешние и вогнутые углы. Можно использовать общий контур или композицию поверхностей, но швы, наложенные двойные рамки и обрезка взаимодействующих объектов недопустимы. Геометрия подложки принадлежит host.

Чат — компактная кнопка поверх нижнего правого края собственной карточки; не вытесняет счётчики. Базовый цвет постоянный, новые сообщения обозначаются счётчиком и мягкой индикацией с учётом reduced motion.

Доступный viewport вычисляет один host адаптер, включая `visualViewport`, fullscreen и системные поля. По принятому для S23 требованию в горизонтальном fullscreen левое поле используется всей компоновкой, включая шапку; запреты на попадание интерактивных целей в фактически перекрытую вырезом область проверяются отдельно. Пак не вычитает safe area повторно. При недостаточной ширине применяется общий компактный профиль с явно определённым переполнением, а не отрицательная ширина зон или произвольное уменьшение карт.

## Выравнивание и расширения

Будущий публичный набор должен предоставлять чистые операции над прямоугольниками: внутренние поля, деление на строки/колонки с общим gap, вписывание с сохранением пропорций, выравнивание краёв/центров и привязку к именованному якорю. Входы и результаты — локальные координаты одной явно заданной зоны; преобразование в viewport делает host. Чистые операции не читают DOM, состояние правил, время или скрытые объекты. Отрицательные размеры и пересекающиеся обязательные зоны дают диагностируемую ошибку, а не молчаливую перестановку.

Расширение выбирается семантическим профилем и ограниченным набором привязок. Его необходимо описать и проверить, прежде чем предлагать автору API. Произвольный callback, который каждый кадр перестраивает весь экран, не является целевым механизмом расширения.

| Игра/геометрия | Обоснованное расширение |
|---|---|
| Лудо | Все карточки без копии `self` привязаны к своим базам. Слева зелёная выровнена нижним краем с базой, жёлтая верхним; аналогичные привязки остальных баз задаются данными. Кубики по центру зарезервированной области под синей карточкой, даже если игрок отсутствует; без отдельной подложки. |
| Косынка | Центральная область — tableau с нормальными промежутками колонок; справа дома одним рядом и крупные действия посередине, слева колода и сброс. Не растягивать карты/зазоры для заполнения всего пространства. |
| Паук | Собственный профиль пасьянса сохраняет tableau; счётчики справа от добора: очки/действия в первой колонке, серия во второй. Статус остаётся общим под названием. |

Это список принятых требований, а не game-ID ветки для общего движка. Новая игра с теми же потребностями должна использовать тот же профиль или якоря без изменения host.

## Жизненный цикл и точечные обновления

1. Host получает только разрешённую сцену, профиль и геометрические резервы. Идентичность сохраняется через `EntityRef`; скрытая рука резервирует количество/размеры, не приватный HTML или ID.
2. Начальное размещение вычисляет зоны и необходимые измерения. Видимый набор действий и компонентов получает стабильные ключи.
3. Выбор карты, счётчик, готовность и сообщение обновляют только зависимые регионы. Они не разрешают перерасчёт поля, повторное исполнение правил или копирование истории.
4. Реальная смена viewport/масштаба, геометрии ассетов либо явно разрешённое действие инвалидируют необходимые размеры. Неизменённые узлы, фокус, прокрутка и перенос сохраняются; при несовместимом изменении перенос явно отменяется.
5. Уход/смена viewer освобождает наблюдатели и отложенные измерения, очищает приватное содержимое. Поздние callbacks не меняют следующую сцену. Анимация использует текущие разрешённые anchors и не запускает второй цикл правил.

## Порядок миграции и приёмка

Сначала Стихийная потасовка (2 и 8 участников) как пример стандартного профиля; затем UNO/Дурак и остальные общие игры; Лудо и пасьянсы подтверждают расширения. Это приоритет работ, не отметка об их завершении.

Для каждого переноса записать: фактический профиль/экспорт, удалённые паковые дубли, использующий его пример, точные app/pack версии и выполненные сценарии. Сравнить одинаковое состояние на измеренных S23 viewport: Chrome, PWA и fullscreen, обе ориентации, один бот и максимум участников рядом. PWA portrait — основной визуальный ориентир. Снимки desktop-эмуляции не доказывают быстродействие физического телефона или настоящую Android-компоновку.

Геометрические проверки: одинаковые внешние зоны при смене числа игроков; квадратное поле; закреплённая карточка `self`; максимум три колонки в portrait; отсутствие обрезанных элементов/наложений; читаемые имена и счётчики; корректная история и safe area. Сценарии обновлений отдельно проверяют сохранение узлов поля/руки и отсутствие лишних измерений при локальном выборе, в течение раунда и при смене ориентации. Приёмка каждой возможности требует реального использования в игре; наличие этого документа не закрывает замечания галереи.


### Уточнение review preview.5

Системные зоны имеют рамки: одна общая в portrait, две равновысокие в landscape; системные кнопки44×44 в обеих ориентациях. Статус находится внутри блока heading, включая счётчики пасьянсов. `data-scene-status="always"` переносит авторизованные счётчики в host-статус в обеих ориентациях; `portrait` сохраняет прежнее ограничение. Паук использует always, серию слева от середины и действия справа. `layout.overrides.opponentsAlign: 'end'` — явное исключение для нижних мест Морского боя; аватары обеих сторон30px, флот противника справа. Рамки/статус/позиция чата/компактные численные счётчики принадлежат host.

При переходе в fullscreen движок сохраняет последнюю измеренную ширину собственной боковой зоны в landscape. Увеличение высоты поля перераспределяет оставшееся пространство со стороны оппонентов; рука, быстрые действия и памятка не меняют ширину только из-за fullscreen.


### Ограниченные профили экрана (preview.7)

Движок выбирает ровно один data-screen-layout: standard, bases, field-only, player-only. Ориентация — независимое data-screen-orientation. Число игроков меняет только колонки списка. Две формы общей карточки (обычная и узкая) выбираются по доступной ширине и одинаковы при наличии/отсутствии руки.

Пак объявляет только затронутые элементы в layout.overrides. Допустимы fieldColumns:3, opponentsAlign:'start'|'end', playerIndicators:'below-avatar', mirrorIndicators:boolean. Неизвестные ключи и значения отклоняются. По умолчанию overrides пуст.

- Морской бой: layout.overrides={opponentsAlign:'end',playerIndicators:'below-avatar',mirrorIndicators:true}. Поле, шапка, собственная карточка и действия используют стандарт.
- Косынка: layout.overrides={fieldColumns:3}. Пак размещает стопки в предоставленных колонках собственными стилями; общие системные зоны не меняются.
- Паук: field-only, стандартные системные зоны; счётчик серий и игровые действия занимают свободную середину шапки.
- Лудо: layout.seats и duplicateSelf задают якоря баз. Движок выполняет правила общих якорей.

Владельцы: game-screen.js — выделение зон и фиксация сетки; game-frame-021.css — системные зоны и единая геометрия карточки; element-sizes.css — физические размеры предметов; interface-scale.css — масштаб и поверхности меню. Из старых стилей удалены 192 конкурирующих структурных объявления карточек. Карточка не меняет форму при добавлении руки; рука добавляется ниже.

В landscape собственная карточка внизу, рука перед ней, действия над рукой. Оппоненты сверху, если пак явно не переопределил выравнивание. Метаданные не занимают свободную высоту поля. Заголовок и быстрые кнопки имеют высоту 60 px, системные кнопки — 44 px.

Матрица S23: Chrome с адресной строкой, PWA, fullscreen, две ориентации (6 вариантов). Дополнительные замеры Chrome со скрытой строкой не снимаются.
