# LAN-01 — долговечное сохранение сетевой партии · контракт 0.15

**Статус:** реализовано в стабильном 0.15. Хостовый журнал, receipts и восстановление комнаты проверяются совместным набором. Этот документ описывает контракт хранения; остатки reconnect перечислены в [Roadmap](ROADMAP.md).

## Принятое решение / ADR

- Не добавлять сервер, Node-хост, relay или интернет-инфраструктуру: authority остаётся в браузерной вкладке хоста WebRTC. Сетевой host-authoritative store работает **только в IndexedDB origin браузера-хоста**.
- Инициализация host Session пишется **до** выдачи первого доступного игрового snapshot. Хранится ID комнаты и Session, точная версия пака, исходная конфигурация, участники и их места на момент старта.
- Каждое успешное действие проходит `Session.prepare(actor, action)` (без изменения живого состояния), далее **одну IndexedDB-транзакцию** `sessions + steps + receipts`, и только после `tx.oncomplete` — `Session.commitPrepared`, публикацию revision и окончательное ACK.
- Успешная квитанция и state transition атомарны. В транзакции проверяется ожидаемая последняя revision, уникальная пара `sessionId/revision` и уникальная тройка `sessionId/viewer/commandId`. Неуспешный дубль abort-ит транзакцию. Отказы и stale-команды также получают сохраняемые квитанции, если запись доступна.
- `steps` содержит последовательные **полные состояния после каждого действия**; `initial` содержит состояние на старте. Хранение инкрементальное, **без повторной сериализации всей истории на каждом ходе**. `load` собирает полную историю, проверяет непрерывность revisions, затем пропускает её через `TabletopSession.restore` с точной версией пака.
- При чтении журнала дополнительно сверяются идентичность комнаты/игры, корректность командных квитанций и **одна уникальная успешная квитанция на каждую подтверждённую ревизию**. Неполное или несогласованное сохранение не используется для запуска authority и не удаляется автоматически. Это защита от повторного исполнения старого хода при повреждённом хранилище, а не криптографическая подпись данных.
- Read-only список `NetworkSessionStore.list()` показывает только метаданные; полный state и журнал не уходят через RTC, QR, страницы Стола или чужого игрока. Пользователь хоста может открыть «Сетевые сохранения хоста» в главном меню и проверить читаемость архива.
- Транспорт `PlayroomWebRTCTransport.serve` поддерживает async `dispatch`; локальный sync-путь ботов/hot seat без хранилища оставлен без изменения.

## Формат IndexedDB

База `playroom.network-host.v1`, schema version 1. Stores: `sessions` (key `sessionId`), `steps` (compound key `[sessionId, revision]`) и `receipts` (`[sessionId, viewer, commandId]`). Вся запись хоста, включая личные state, seed, скрытые руки и квитанции, — **приватные данные доверенного origin**. Не раздавать их WebRTC-клиенту. Утечка через бэкап хоста и вредоносный JS того же origin вне данной модели защиты.

Нет тихого fallback на `localStorage`: если IndexedDB заблокирован или QuotaExceededError, сетевой старт/ход завершается явной ошибкой, без ложного ACK. Это не влияет на существующие локальные боты, hot seat и сохранения `playroom.session.v1`/`playroom.paused.v1.*`. `file://`/`content://` могут не обеспечить стабильный origin — для долговременной игры предпочтительнее установленная PWA с устойчивым origin. Очистка site data уничтожит архив; перенос на другой URL/устройство не сделан.

## Продолжение сетевой комнаты после перезапуска — новая итерация

В рамках PR #27 запись начатой сессии получает приватный `RoomService.exportRecovery`:
состав комнаты/места, токены только для возврата гостей и неизменную идентичность
комнаты. При открытии сохранения хост с тем же профилем может продолжить игру
через `RoomService.restoreRecovery`, `TabletopSession.restore` и `SessionAuthority`
с новой `authorityEpoch`. WebRTC-соединения не переживают закрытие браузера,
поэтому гости повторяют прежний QR-pairing и предъявляют сохранённый `resumeToken`;
по одному никнейму занять чужое место нельзя. Все секреты остаются в приватном
IndexedDB хоста и не включаются в публичный снимок или QR. Старые архивы без
списка токенов продолжают читаться, но повторный запуск комнаты запрещён.

Если **до первого сохранения** нет места/версии игры, не открылась IndexedDB или
пак не активировался, хост отменяет старт и возвращает согласованное лобби.
Если начальная запись уже зафиксирована, но UI/подписка на authority не
инициализировались, хост не создаёт поверх неё вторую партию: закрывает
незавершённые соединения и предлагает перезагрузку с явным восстановлением
по уже записанному ID. Это отличает несостоявшийся старт от сбоя после commit.

Квитанции команд восстанавливаются из `receipts`. Для **уже принятой** команды со
старым epoch разрешено только вернуть ту же квитанцию, без исполнения второго
хода; неизвестная команда старого epoch отвергается. Ротация гостевого токена
записывается транзакционно до выдачи подтверждения. При потерянном ответе
предыдущий токен может быть повторно использован для **отключённого** места
в течение 120 секунд (защита от потери ответа в момент перезапуска); пока место
подключено, старый токен не даёт перехватить его. Несовпадающие токены не
принимаются. Обе страницы хоста не могут одновременно владеть той же authority,
если origin поддерживает Web Locks; при отсутствии Web Locks старт блокируется,
а не обещает защиту без неё.

Добавлены `tests/host-recovery.test.cjs` и отдельные сценарии реального Chromium в
`network-session-store-browser.test.cjs`: восстановление состава, токена и
хоста на прежнем origin, эксклюзивная Web Lock и квитанции старого epoch. CI на
новом SHA ещё обязателен; физическая приёмка PWA/Android, лимиты IndexedDB и
автоматический ICE restart не объявлены готовыми.

## Границы и дальнейшие проверки

Durable команды ботов используют actBotAsync и тот же атомарный путь, что команды людей. Пауза сохраняется authority; квоты пауз и игровые часы остаются в Roadmap. Синхронный actBot не используется для durable authority.

Host recovery, receipts, приватность и блокировка второй вкладки покрыты браузерными проверками. Матрица физических Android/ПК (сон, фон, квоты, перезапуск PWA, разные origin) остаётся отдельной приёмкой. Retention, компактные checkpoints и экспорт на другое устройство — будущие задачи; повреждённые записи не удалять автоматически.

Любое изменение записи/восстановления требует полного совместного прогона на текущем SHA. Новое RTC-подключение после host restart остаётся необходимым до появления защищённой внешней сигнализации.

## Идентичность установленного пака (0.15)

При новом сетевом старте вычисляется SHA-256 **полного установленного пакета** через `TabletopPacks.exportPack` (включая `rules.js`, `view.js` и ресурсы), записывается вместе с initial snapshot и проверяется до восстановления authority. Одинаковый `id@version` с иным содержимым больше не даёт продолжить сессию. Старые экспериментальные архивы без digest остаются доступными для чтения, но не получают разрешение на продолжение. Хеш не является авторской подписью или песочницей стороннего JS.


## Разработка 0.18: квитанции публичного Стола

Схема БД пока прежняя. Поле receipts.viewer обозначает индекс исполняющего игрока: для команды Стола в нём записан actor, тогда как сетевой snapshot по-прежнему viewer=-1. Signature содержит исходный actor, поэтому повтор после смены хода/восстановления authority находится в том же журнале и не создаёт второй step. ACK строится по capability Стола и не выдаёт приватную проекцию actor. Переименование этого временного поля и явный receipt scope относятся к переносу CommandProcessor/journal. Регрессия `Table public commands survive IndexedDB reload` использует реальную IndexedDB и перезагрузку страницы.
