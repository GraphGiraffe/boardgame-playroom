# Сеть 0.20: четыре этапа и тестовый preview.10

Стабильный выпуск приложения не публиковался. Владелец настроил живой Supabase, Edge Function/Vault и включил Push: тестовое уведомление получено на Android. Тестовая PWA доступна через временный Tailscale Funnel; карточки этапов остаются на проверке.

| Этап | Что готово | Что требуется на сервере |
| --- | --- | --- |
| Уведомления | Сообщения, приглашения в группу/игру, события чата комнаты; явное включение устройства, переход в чат, защита от повторов и смены аккаунта | SQL + отдельная настройка Push-доставки |
| Передача хоста | Добровольная передача в лобби и во время партии, согласие преемника, прямой перенос по WebRTC, сохранение мест и настроек | Только для Онлайн: существующие signaling/online/host-transfer RPC; для Сетевой Supabase не используется |
| Временные боты | Хост подключает бота к отошедшему/отключённому месту; игрок явно возвращает управление после принятого хода | Новая SQL-миграция не нужна |
| Перенос сохранений | Файл с точным паком; независимая локальная копия либо readonly история участника, без resume-ключей | Новая SQL-миграция не нужна |

## Серверная подготовка: текущая 0.21 и история 0.20

Для обновления существующего проекта до 0.21 использовать [SERVER-ROLLOUT-MANIFEST.md](ux-021/SERVER-ROLLOUT-MANIFEST.md): проверка baseline и read-only preflight, затем согласованные узкие обновления. Текст о настроенном Push выше — историческое свидетельство 0.20, не проверка текущего production. Полный setup ниже нужен только для отдельно согласованного полного развёртывания.

1. В проекте PlayRoom открыть **SQL Editor → New query**.
2. Вставить **весь** `setup-supabase.sql` из текущей сборки и нажать **Run**. Он повторяемый, сохраняет данные и существующую настройку Push. Все исходные миграции из текущего `tooling/supabase_setup.py` идут в одной транзакции; в конце обновляется schema cache API. Старые отдельные SQL-файлы дополнительно запускать не нужно.
3. В новой query выполнить `check-supabase.sql`. В текущей сборке будет 19 строк: 18 функций и один trigger. В каждой **installed = true**, **exact_match = true**. `arguments` показывает сигнатуру; дополнительные/ложные строки означают, что нужно проверить применённую схему, а не повторять старую миграцию вслепую.

Полный актуальный список SQL задан `MIGRATIONS` в `tooling/supabase_setup.py`, включая расширение host-transfer Push и последующие cloud/account/registration/ICE миграции; прежние шесть файлов — исторический состав 0.20. Сборщик `tooling/supabase_setup.py` используется обычным `build.py`; ручной копии схемы нет. Проверка сравнивает тела ключевых функций, а не объявляет весь удалённый проект проверенным.

## Чтобы Push действительно доставлялся

Один SQL подготавливает подписки, очередь и RPC. Он не создаёт VAPID-ключи и не разворачивает функцию отправки.

По [инструкции Push](../server/push/README.md) отдельно:

1. Для нового развёртывания создать закрытый env-файл с ключами и контактным email. При обновлении использовать существующие ключи и файл; повторная генерация потребует новых подписок устройств.
2. Загрузить секреты и развернуть `playroom-push` в Edge Functions.
3. Создать `playroom_push_url` и `playroom_push_secret` в Vault.
4. Выполнить **enable-web-push.sql** из сборки, затем включить `playroom_push_config` с публичным VAPID-ключом.
5. Открыть PWA по HTTPS, войти и включить уведомления на устройстве.

`enable-web-push.sql` — отдельный необязательный шаг, выполнять после настройки функции/Vault. Секреты не вставлять в общий setup и не отправлять в чат. После этого нужна проверка на двух реальных устройствах. На тестовом проекте доставка уже настроена владельцем; Android получил тестовый Push. Это не подтверждает все события и все устройства.

## Проверка кода и границы

Исправлены запоздалый Push-config при смене аккаунта, порядок сообщений worker при задержке регистрации, повторное открытие закрытого импорта при ошибке, незакрытый IndexedDB при импорте истории и диагностирование некорректного кадра. Каноническая сериализация JSON переиспользует Protocol; сборка SQL единая.

Модули разделены: application — сценарии/контейнеры, core — authority/валидация контроллеров, platform/web — хранилища/RTC/worker, app — окна и адаптеры, server/supabase — схема и отправитель. В новых runtime-модулях не найдены точные копии, отладочные console/debugger, TODO/FIXME или пути к tmp_files. Проверка точных копий не доказывает отсутствия любого смыслового дублирования во всём проекте.

15 актуальных адресных проверок прошли, включая общий SQL дважды. Реализация передачи хоста/ботов сверена с ранее проверенной сборкой по файлам; её результаты переиспользованы. Полный набор автоматически не запускался. Отдельно проверяется готовая PWA/offline HTML, ZIP и SHA256.

Ограничения: аварийного выбора хоста нет; при выключенном хосте бот на его устройстве не работает. Перенос файла не восстанавливает действующую онлайн-комнату. Реальные NAT/мобильная сеть, managed pg_net/Vault/cron и внешний Push-провайдер требуют живой приёмки.

Подробности: [передача хоста](HOST-TRANSFER.md), [боты](TEMPORARY-BOT.md), [сохранения](SAVE-TRANSFER.md). Далее по 0.20 — STUN/TURN в конце и общая приёмка. Таймеры и новые паузы остаются в 0.21.

## Вход в комнату: preview.8

«▶ Войти» из личного/группового приглашения и каталога открывает подключение, затем лобби с текущим никнеймом. Отдельного промежуточного списка приглашений нет. Принятое личное приглашение сохраняет повторный вход. Каталог комнат обновляется автоматически, ручной RTC-вход доступен по Wi-Fi в заголовке. Каталог и быстрый вход совместно ждут одну гостевую авторизацию; параллельная загрузка не возвращает ошибку busy. Повторное нажатие ждёт ту же попытку; закрытие отменяет её, ожидание ограничено 45 секундами. Ошибка оставляет кнопку повторения.

Проверены реальный RTC на одной машине, отмена/повтор, защита уже активной комнаты, заявка в друзья и скриншоты 320/390 px и альбомного экрана. Причина неудачного подключения телефона к Ember по старому SDP не установлена: срок его хранения истёк. Повторная живая приёмка через мобильную сеть остаётся обязательной. Для этих клиентских изменений SQL повторно выполнять не требуется.

## Новые события preview.8

Push охватывает сообщения и приглашения в личных/групповых/комнатных чатах, заявку и принятие дружбы, вступление в группу, принятие приглашения в игру, начало/продолжение/завершение партии и «Ваш ход». Социальные события фиксируются в транзакции сервера. Игровые — только действующим хостом после сохранения хода. В очередь не передаются карты, варианты действий или приватные проекции. Право на ход определяется доступными обычными действиями игрока; отдельные реакции не превращаются в «Ваш ход». Боты и зрители исключены.

Уведомление о ходе отменяется, если очередь уже дошла до следующего игрока, включена пауза, закончена/закрыта партия или участник вышел. Повторы публикации не создают новый Push; промежуточные действия активного игрока не спамят. Начало/продолжение отправляются остальным участникам, активному игроку — одно «Ваш ход». Сервер отправки и VAPID остаются прежними; для 0.21 использовать текущий server rollout manifest; историческая проверка 10 функций не заменяет нынешние 19 строк.

Карточка выбранных параметров находится перед правилами; полный нижний раздел остаётся. Изменённые хостом параметры показываются поверх экрана с предыдущими и новыми значениями. Фоновый RTC-reconnect сохраняет главный экран/чат/черновик; явное переподключение Онлайн использует облако. Повторный вход в другую комнату блокируется, дублирующие кнопки комнаты и громоздкий блок нового приглашения убраны.


## Исправления preview.9 и граница транспорта

Ходы, проекции, ACK, история, сообщения/реакции комнаты и подготовка передачи хоста идут через WebRTC. Supabase обслуживает идентичность, членство, поиск/сигнализацию, личные и групповые сообщения, Push и атомарные серверные права. Хост отправляет разрешённые уведомления о партии, а не полную приватную Session.

Серверная авторизация больше не задерживает каждый игровой RTC-пакет. После первоначальной проверки выданное соединению право проверяется локально; существующий host-loop перепроверяет членство в фоне. Временная ошибка API сохраняет соединение, явный запрет/закрытие комнаты отзывает его. При недоступном облаке серверный отзыв будет обнаружен после восстановления API; локальные правила authority продолжают проверять команды.

Повторное подключение сохраняет отключённый UI до успешного resume, позволяет выйти в меню и не открывает лобби автоматически. Онлайн-архив участника хранит cloudRoomId/accountId отдельно от кадров; после перезапуска продолжение использует облачную комнату. Resume-секреты в кадры, QR и переносимый архив не включаются.

Восемь видео разобраны; исправлены источник анимаций +2/+4 и пустая колода UNO (без подписи и вложенной кнопки). Живой тест через Funnel/Supabase: открытая комната, ход через RTC при блокировке HTTP Supabase у хоста, обрыв, выход, восстановление в фоне, повторное открытие страницы и возврат на прежнее место, закрытие комнаты и выход. Это два браузера на одном компьютере, не подтверждение работы двух мобильных сетей.

Сборка: `tmp_files/online-video-review-020/build/`, отчёт `tmp_files/online-video-review-020/REPORT.md`. Новая SQL не требуется. Прежние 14 паков сохранены без изменений; новый UNO 0.6.7-preview.1 применяется в новых партиях, старые сохранения сохраняют точную прежнюю версию.

## Preview.10: общая приёмка, правила и темы

Окно называется «Правила» во всех контекстах. Выбранные настройки остаются сверху; оглавление ведёт к разделам и нижним пояснениям параметров. Быстрые действия: наверх, оглавление, параметры. Переходы прокручивают только окно и не меняют URL/историю возврата. Общие параметры идут первыми; числовые и именованные варианты выводятся одинаковой строкой «Варианты: …».

Новые паки могут собирать Markdown-правила в прежние структурированные блоки (см. соседний packs/docs/AUTHORING.md). Прежние JSON-правила и динамические подсказки не преобразуются. Конвертер отключён, пока автор явно не объявит `.md`; 15 прежних исходных паков дают прежние байты сборки при использовании нового компилятора.

На живом тестовом Supabase найдено повторное использование группового приглашения личным. В playroom_online ограничен поиск личного приглашения условием group_message_id is null. Минимальная повторяемая SQL-правка применена через MCP; полная setup-схема содержит тот же результат. Схема таблиц и данные прежних пользователей не переписываются. У гостя также сохраняется игровая кнопка комнаты; дедупликация применяется только к главному экрану. Баннеры сообщений исчезают через 6 секунд без отметки прочтения.

Проверены два временных зарегистрированных QA-аккаунта: личные/групповые сообщения, идемпотентность и delta-загрузка, отметки чтения, дружба, одинаковые имена групп, вход/отклонение приглашений, закрытие последним участником; настоящая облачная комната, RTC при недоступном API, обрыв/возврат, reload на прежнее место, временный бот и возврат, передача хоста с продолжением хода. Аккаунт владельца не используется. Локальные проверки и живые замеры не являются подтверждением Android/NAT-сетей или доставки каждого Push на телефон.

Тема задаёт фон html/body и color-scheme; отдельный ранний скрипт использует сохранённые цвета до основного runtime. Worker отдаёт theme_color/background_color сохранённой темы в манифесте, сохраняя id, start_url, scope и icons. Момент обновления нативной заставки Android выбирает Chrome/WebAPK; это не обещание мгновенного изменения установленного приложения. Физическую белую полосу Android и нативную заставку нужно проверить на телефоне после обновления preview. Исправлены также несуществующие ссылки на цвета палитры: карточка параметров, счётчик сообщений, выделение примеров, ошибки и границы.

Подробный отчёт: tmp_files/rulebook-online-020/REPORT.md. Preview.10 предназначен для тестового Funnel, стабильной публикации нет.

### Размер клиентских архивов · preview.11

`application/replay-codec.js` хранит уникальные проецированные события в общем пуле, а в кадрах — числовые ссылки. `state.events` и `events` восстанавливаются точно, даже если их наборы различаются. Правила и закрытое состояние хоста не используются для восстановления.

Переносимый replay: `playroom-save` v2, payload encoding `event-pool-v1`. По умолчанию экспорт содержит `pack:null` и точную зависимость id/version/SHA256, которую импорт разрешает через установленный менеджер паков. Отсутствующая версия даёт `SAVE_PACK_MISSING`, подмена на текущую версию запрещена. Переключатель автономного переноса включает пак целиком. `application/save-compression.js` дополнительно сжимает весь файл в контейнер v2 `gzip-base64-v1`; если CompressionStream недоступен или сжатие невыгодно, экспорт остаётся несжатым компактным v2. Импорт v1 и локальных session-файлов сохранён; экспорт session остаётся v1. Для импорта v2 требуется preview.11+, для сжатого контейнера — DecompressionStream. Проверка SHA256 выполняется над контейнером и его содержимым до декодирования, лимит распаковки и развёрнутых кадров — по 48 МиБ; вложенные контейнеры запрещены.

Клиентская IndexedDB остаётся v1: поле `eventPool` в записи матча и кодированные кадры обновляются одной транзакцией. Старые кадры уплотняются в транзакции чтения без потери дыр в истории, курсоров и сетевого контекста. Пул не выдаётся в библиотечный список. SQL не требуется.

## Добровольная передача хоста

В сетевой и онлайн-комнате хост открывает настройки комнаты → «Передать роль хоста», выбирает подключённого игрока, а тот подтверждает принятие. В лобби передаются настройки, места, чат и права восстановления подключений; готовность людей снимается. Во время партии только выбранный преемник получает полный журнал и закрытое состояние. Передача идёт по WebRTC. В Онлайн Supabase фиксирует согласование смены владельца существующей комнаты, без загрузки журнала партии; код, пароль и приглашения сохраняются.

Автоматическая передача после аварии отсутствует: полное закрытое состояние не реплицируется всем участникам. Восстановление подготовленной добровольной передачи после сбоя не является выбором нового хоста после аварии. Обычные механизмы переподключения к прежнему хосту сохраняются.

Для ручных проверок комнат по умолчанию: средний бот, включённый автостарт; Ember занимает место зрителя, если не проверяется другая роль.


## Регистрация и заявки в друзья · 0.20.1-preview.1

После полного setup применяется `registration.sql`: публичный RPC возвращает только доступность имени, а trigger создаёт профиль в той же транзакции, что и auth.users. Новая форма требует имя; старые клиенты и существующие аккаунты сохраняются. Имя из metadata используется только для отображения и поиска, никогда для авторизации.

В живом проекте владелец отключил Confirm email; mailer_autoconfirm=true подтверждён через публичные настройки Auth. SMTP не настроен: восстановление пароля письмом по-прежнему зависит от ограниченной встроенной отправки. Это настройка Dashboard, а не SQL-миграция.

Заявки и принятие исходящей заявки используют существующий unread poll и отдельное локальное состояние по аккаунту. Системный Push открывает профиль участника. Политика разрешений уведомлений не меняется; новые таймеры/опросы сервера не добавлены.
