# DEPLOY-01 — автоматическая публикация закрытой PlayRoom PWA в Cloudflare Pages

**10.10.2026 · Статус: запланировано, НЕ настроено в GitHub/Cloudflare.** Текущая физически проверенная схема — ручной Direct Upload ZIP в уже созданный проект Cloudflare Pages. После исправления `_worker.js` вход по паролю сработал, PWA установлены на двух устройствах. Существующий URL/имя проекта и параметры учётной записи **нужно сверить в аккаунте**, не угадывать по обрезанному скриншоту.

## Цель и границы

- Публиковать **тот же точный протестированный PWA-артефакт** из GitHub Pre-release, а не собирать произвольный `dev` без гарантированных пяти паков. Последний подтверждённый релиз: [`v0.15.0-rc.8`](https://github.com/GraphGiraffe/boardgame-playroom/releases/tag/v0.15.0-rc.8), release SHA `85f4199c1d1d3b8cc17d550281d5174a1dfcded5`; [CI 466/466](https://github.com/GraphGiraffe/boardgame-playroom/actions/runs/38008718811).
- **Не удалять пароль:** Cloudflare `_worker.js` в Pages Advanced Mode обязан проверять авторизацию для HTML/JS/игровых данных перед `env.ASSETS.fetch(request)`. Вариант Android может позволить неавторизованную загрузку **только** иконок и `manifest.webmanifest` для установки PWA — это явный компромисс.
- Сохранять **один production origin**: смена `*.pages.dev`, scheme, hostname, path/scope или порта может поменять доступность IndexedDB, Service Worker, прав гостя и установленных игр. Обновления — новый deployment **того же** проекта, не новый Pages-проект.
- Статический Cloudflare Pages **не** является сервером комнаты, сигналингом WebRTC, STUN/TURN или системой LAN-03. Прямой RTC может по-прежнему требовать PR3/нового QR.

## Рекомендуемый pipeline (предложение для отдельной реализации)

1. Источник — **immutable GitHub release** (tag + SHA + SHA256SUMS), только после завершения publisher со статусом `success`. Для первого запуска — явно выбранный вручную `v0.15.0-rc.8`; для будущих RC — привязка к новому опубликованному релизу по событию или разрешённый ручной promote, без сборки по каждому push.
2. Авторизованная CI получает `playroom-pwa-<version>.zip` и `SHA256SUMS.txt` из релиза, валидирует SHA-256 по **байтам скачанного ZIP** и проверяет распаковку (корень — `index.html`, `sw.js`, `manifest.webmanifest`, пять известных паков в `installed-packs.js`). Не доверять имени файла без хэша и происхождения.
3. В **чистую** директорию готовой PWA добавить прошедший аудит защищённый `_worker.js` (обработчик пароля/сессии) из **приватного CI-секрета либо отдельно управляемого закрытого исходника**. Worker, подпись cookie и конфигурация доступа должны проходить отдельные тесты: запрос к `/` и произвольному `/app/*.js` без сессии — отказ/вход, неверный пароль/поддельная cookie — отказ, правильная сессия — выдача нужного файла. Никакой fallback, отдающий защищённые assets открыто при сбое Worker.
4. Выпустить **preview**, проверить физически вход в PWA (Android Chrome/WebAPK), точность версии, offline-cache и права клиента. Лишь после явно успешного gate — **production deployment**. До реализации gate не включать автоматический production на каждый push.
5. Загружать уже подготовленную директорию через официальный Wrangler: `npx wrangler pages deploy <DIR> --project-name=<PROJECT> --branch=<PRODUCTION_BRANCH>` с `CLOUDFLARE_ACCOUNT_ID` и `CLOUDFLARE_API_TOKEN` в секретах CI; сначала убедиться в значении production branch реального Direct Upload Pages-проекта. Документация: [Cloudflare Direct Upload с CI](https://developers.cloudflare.com/pages/how-to/use-direct-upload-with-continuous-integration/), [Advanced Mode `_worker.js`](https://developers.cloudflare.com/pages/functions/advanced-mode/).
6. После загрузки проверить HTTP-пути **по живому адресу** без аутентификации и с ней, service-worker/cache, успешный и запрещённый вход. Сохранить deployment ID, release tag/SHA, URL, проверенные checksums и доступный rollback. Не удалять IndexedDB клиентов и не менять прежний тег RC.

## Предпосылки и безопасность — блокеры активации

- Владелец проекта сам передаёт **только в защищённые настройки CI/Cloudflare**, а не в чат/коммит: `CLOUDFLARE_ACCOUNT_ID`, Cloudflare API token с минимальным `Account / Cloudflare Pages / Edit`, точное `CLOUDFLARE_PAGES_PROJECT` и проверенная production-ветка.
- Рабочий **исправленный** password Worker из текущего загруженного protected ZIP необходимо перенести в контролируемый закрытый процесс сборки с ревью/тестами. **Не** коммитить пароль, производные для перебора, ключ подписи, переменные окружения, личные токены или готовые закрытые ZIP в публичные ветки. Настроить ротацию пароля/ключа и TTL сессии. Если секретов нет — **fail closed** и **не deploy**.
- Для GitHub Actions нужен документированный механизм запуска **на default branch** либо явный ручной триггер, работающий с фактической конфигурацией: одно добавление YAML в `dev` не включает автоматически событие `release.published`. Не изобретать секретные токены и не добавлять безусловный workflow, который сделает открытую PWA публичной. До согласования допускается локальный защищённый upload Wrangler.
- Проверить, что production, preview и URL ранее опубликованных deployment-ов подчиняются требуемой политике доступа. Не полагаться на секретность адреса `pages.dev`, на JavaScript-форму в `index.html` и на приватность GitHub репозитория.
- PWA может хранить файлы в Service Worker CacheStorage даже после истечения сессии: отзыв доступа не очищает уже загруженные клиентские копии. Для полной защиты прошлых устройств нужна отдельная продуктовая политика.
- Изменение `_worker.js` может повлиять на POST логина, редиректы, cookies, WebAPK и служебные ресурсы. Сохранить regression suite для `Origin: null`, чужих заголовков, CSRF/срока действия/подделки cookie; тесты предыдущего fix не считать доказательством корректности будущей версии.

## Приёмка DEPLOY-01

Новый подтверждённый релиз автоматически или одним разрешённым ручным promote появляется **на том же production URL**, только если SHA/структура/парольный Worker прошли gate; без пароля HTML/JS недоступны по прямому URL, с правильным паролем PWA запускается на двух устройствах; установленная ранее PWA обновляется без потери сохранений; при провале проверок предыдущий защищённый deployment остаётся активен. Логи не раскрывают секреты.
