# PlayRoom 0.15.0-rc.2 — звуковое сопряжение WebRTC (LAN)

## Назначение

Pairing без обмена длинными ссылками и QR: **хост воспроизводит Offer**, телефон слушает микрофоном, **телефон воспроизводит Answer**, хост слушает. После двух сообщений устанавливается штатный `RTCDataChannel`; **игровые данные и скрытые руки никогда не передаются звуком**. Интернет/RoomHub/Node-сервер не нужны для звуковой сигнализации или дальнейшего прямого подключения.

Это **альтернативный способ сигнализации**, а не отдельный игровой/сетевой движок. QR, Web Share и copy/paste остаются fallback. Существующие паки игр и протокол команд не изменяются.

## Пользовательский путь

1. Запустите **одну и ту же офлайн HTML/PWA PlayRoom** на устройствах одной локальной Wi-Fi сети; в поддерживаемых браузерах разрешите микрофон. Для PWA используйте HTTPS, localhost — для разработки.
2. На ПК/телефоне хоста создайте сетевую комнату и выберите **Подключить устройство**. Выберите LAN IPv4 и Tx protocol (по умолчанию `Fastest`). Браузер показывает известные ему IPv4 ICE-кандидаты, предпочитая 192.168.x.x и 10.0.x.x. При скрытии адресов браузером (mDNS) укажите фактический IPv4 вручную, из свойств Wi-Fi сети. Не подставляйте вымышленный адрес.
3. На клиенте откройте **Присоединиться к комнате → Слушать звуковое приглашение** и разрешите микрофон. Нажмите на хосте **Передать звуковое приглашение и слушать ответ**.
4. После звукового Offer выберите IP самого клиента (или введите вручную), при необходимости смените Tx protocol и нажмите **Отправить звуковой ответ**.
5. После открытия WebRTC DataChannel появится прежний экран лобби: вход, выбор места, готовность и старт партии. Повторите приглашение для каждого нового телефона.

**Важно:** два устройства должны находиться рядом в пределах слышимости и иметь прямую сетевую достижимость. Guest Wi-Fi с AP/client isolation может блокировать WebRTC. Пока ограничение WAN/NAT без relay сохраняется.

## Реализация

- `app/acoustic-pairing.js`: versioned binary signaling frame, Base64URL для текстового интерфейса ggwave (не более 140 ASCII-байт), `pack/unpack`, список доступных IPv4 UDP host ICE-кандидатов, восстановление современного SDP.
- `app/vendor/ggwave.js`: локальный JS+inline WASM ggwave 0.4.3, upstream commit `060aec73dd7123ccac200442f75bdc7369795ffe`, MIT; `app/vendor/LICENSE.ggwave` содержит обязательный текст лицензии.
- `app/network-ui.js`: общие окна приглашения/входа, выбор IP/Tx, передача/приём звука и несколько установленных WebRTC-подключений (новое приглашение не закрывает подключённого игрока).
- `index.html`, `sw.js`, `build.py`: модуль входит в автономный HTML и PWA offline bundle. Никаких runtime CDN для **ggwave**.

Звуковой пакет содержит IPv4, UDP-порт, ICE credentials, DTLS SHA-256 fingerprint и UUID приглашения. Фингерпринт обязателен для шифрованного WebRTC. Он не заменяет взаимную аутентификацию неизвестных участников: при подключении в присутствии чужих устройств проверяйте намерение присоединиться. Никнейм и IP не являются игровыми полномочиями.

Tx: `Fastest` по умолчанию, `Fast` / `Normal` по выбору. Слышимый диапазон выбран по умолчанию как более совместимый; ultrasound не включён по умолчанию из-за аппаратных ограничений.

### Ограничения и проверки

- Браузеры могут отдавать только mDNS-кандидаты; обычный сайт **не может гарантированно узнать все реальные IP сетевых интерфейсов**. Ручной ввод обязателен как fallback. Указанный IPv4 должен соответствовать адресу устройства, иначе WebRTC не установится.
- Некоторые браузеры могут не принять восстановленный SDP: это проверяется WebRTC smoke-тестом в Chromium и требует физических тестов Windows Chrome + Android Chrome, Android↔Android и iOS Safari. Результаты не следует выдавать за проведённые до фактических прогонов.
- Разрешение микрофона требуется явным действием. Не передавайте секреты доступа к игре непосредственно в звуковом пакете: звук доступен другим людям рядом.
- Пока нет автоматического reconnect после рестарта host вкладки; это отдельные задачи LAN-01/02/03. Сохранение и история также не реализуются данной feature.
- QR, Web Share и копирование длинных ссылок остаются способом подключения при ошибках звука, нестандартных ICE-кандидатах или несовместимых SDP.

### Проверки

`node --test tests/acoustic-pairing.test.cjs tests/acoustic-webrtc-browser.test.cjs`: двусторонний codec, частные IP, ручной IP при mDNS, отклонение ошибочных данных, WASM-энкодер и реальное Chromium RTCDataChannel.

Затем обычная независимая проверка и полный совместный прогон с установленными исходниками пяти паков. Для выпуска проверять финальные собранные offline HTML/PWA-артефакты и контрольные суммы после добавления внешних assets.
