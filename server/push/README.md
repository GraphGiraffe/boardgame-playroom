# Web Push для PlayRoom

Локальная реализация. Публикация приложения и развёртывание функции выполняются отдельно после разрешения владельца.

Поддерживаются личные и групповые сообщения, приглашения в группы, личные и групповые приглашения в игру. Общий/командный чат комнаты передаёт событие через текущего хоста: он определяет разрешённых получателей, сервер проверяет владельца, действующую аренду хоста и членство. Содержимое комнатного сообщения не уходит в облако: Push содержит только факт сообщения и ссылку на чат. История комнаты остаётся у хоста; закрытая комната не открывается повторно из старого уведомления. Для локальной игры и соединений без облачной комнаты Push не создаётся.

## Подготовка сервера

Нужны существующий Supabase-проект, его обычный CLI и контакт владельца. VAPID private key и секрет вызова функции не входят в HTML/PWA/SQL и Git. Сохраните ключи: их смена потребует повторного включения уведомлений на устройствах.

1. Сначала определить, это новый проект или обновление существующего. Для существующего проекта 0.21 использовать [server rollout manifest](../../docs/ux-021/SERVER-ROLLOUT-MANIFEST.md): read-only preflight, два обязательных узких обновления и два условных расширения Push после проверки baseline. Полный `setup-supabase.sql` предназначен для отдельного согласованного полного развёртывания, а не замены этой проверки. Текущий `check-supabase.sql` содержит 19 строк: 18 функций и один trigger; все installed/exact_match должны быть true. Это проверка известных контрактов, не всей удалённой схемы. Источник состава — `tooling/supabase_setup.py`.
2. Для нового Push-развёртывания создать файл ключей **вне репозитория**. При обновлении работающего отправителя использовать существующий закрытый файл, не генерировать ключи заново:

   ```sh
   node server/push/generate-keys.mjs /private/path/playroom-push.env mailto:YOUR_CONTACT
   ```

   Команда создаёт новый файл с правами 600 и печатает только публичный ключ. Укажите реальный email владельца после `mailto:`.
3. Загрузить секреты в Edge Functions и развернуть функцию из корня репозитория:

   ```sh
   supabase secrets set --project-ref geurlwivdiqboylciqhl --env-file /private/path/playroom-push.env
   supabase functions deploy playroom-push --project-ref geurlwivdiqboylciqhl
   ```

   `supabase/config.toml` отключает JWT gateway только у этой функции. Она сама требует `x-playroom-push-secret`. Встроенные `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` доступны только серверу. Публичные publishable credentials для отправки не подходят.
4. В Dashboard → Vault создать секреты:
   - `playroom_push_url`: `https://geurlwivdiqboylciqhl.supabase.co/functions/v1/playroom-push`;
   - `playroom_push_secret`: значение `PLAYROOM_PUSH_SECRET` из закрытого env-файла.
5. В SQL Editor выполнить `enable-web-push.sql` из сборки (источник: `server/push/enable.sql`). Оно включает pg_net/pg_cron, асинхронный вызов функции при вставке в очередь и повторную проверку раз в минуту. Содержимое сообщений не входит в HTTP webhook: функция сама забирает очередь через закрытый RPC. В тестовой локальной PostgreSQL проверяются очередь и RPC; managed pg_net/Vault/cron требуют отдельной проверки Supabase.
6. Включить конфигурацию, вставив **только публичный** ключ:

   ```sql
   update public.playroom_push_config
   set public_key = 'PUBLIC_VAPID_KEY', enabled = true
   where singleton;
   ```

7. Открыть новую PWA по HTTPS, войти в постоянный аккаунт → Параметры → Уведомления. Нажать действие включения уведомлений и разрешить уведомления браузеру. Включение нужно на каждом устройстве. При запрете изменить разрешение в браузере; повторных автоматических запросов нет. На iOS Web Push требует установленного на главный экран приложения и поддерживаемой версии системы.

## Проверка на двух устройствах

- Включить уведомления на получателе и закрыть приложение. С другого аккаунта отправить сообщение, приглашение в группу, приглашение в игру лично и в группу. Проверить текст и переход в соответствующий чат с актуальной карточкой приглашения.
- Для сообщения комнаты хост должен быть в сети; общий и командный каналы проверять с 3 участниками, включая игрока другой команды. Командный Push не должен приходить другой команде. После выхода из группы/комнаты старые уведомления не должны предоставлять доступ к истории.
- Открытый и сфокусированный нужный чат не должен дублироваться системным уведомлением. Скрытая вкладка должна получать его. Прочитанные до отправки сообщения, отвеченные и истёкшие приглашения убираются из очереди.
- Выключить колокольчик и выйти из аккаунта: устройство отписывается, уведомления закрываются. Войти другим аккаунтом: старые события не показываются. Проверить второе устройство того же аккаунта отдельно.
- При временной ошибке push-провайдера очередь повторяется с задержкой, до 5 попыток. 404/410 удаляют недействительную подписку. Гарантировать строго однократную доставку после падения между отправкой и ACK нельзя; worker хранит последние 200 event ID и подавляет повторный показ.

## Эксплуатация

Все таблицы закрыты RLS и прямыми grants. Клиентский RPC `playroom_push` управляет только подписками текущего постоянного аккаунта; `target` повторно проверяет доступ перед навигацией. Worker хранит только ID аккаунта, ID событий и цель перехода, без auth tokens. Service-role RPC выдаёт аренду задания и принимает результат только с её UUID. Уведомления не содержат паролей комнат, invite/resume tokens или произвольных URL.

Ключи подписок передаются Web Push-провайдерам по стандартному зашифрованному протоколу. Отправитель использует закреплённый `npm:web-push@3.6.7`, разрешает только HTTPS endpoint известных браузерных Push-служб, не открывает пользовательские URL. Уведомления ограничены текущей областью PlayRoom на общем origin. Нажатие не принимает приглашение автоматически.

Выключение сервера: `update public.playroom_push_config set enabled=false where singleton;`. Очередь не забирается, новые сообщения не создают доставок. При окончательном отключении удалить подписки и очередь через административный SQL. При кратковременном выключении до повторного включения учитывайте срок жизни уже накопленных событий.

Источники API: [Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API), [notificationclick](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/notificationclick_event), [Supabase Database Webhooks / pg_net](https://supabase.com/docs/guides/database/webhooks), [web-push](https://github.com/web-push-libs/web-push).

## События preview.8

Сообщения, приглашения в игру/группу, заявки и принятие дружбы, вступление участника в группу, принятие игрового приглашения, начало/продолжение/завершение партии, «Ваш ход». Социальные переходы — серверные triggers; игровые — RPC game-state действующего хоста. Для обновления 0.21 порядок задаёт [server rollout manifest](../../docs/ux-021/SERVER-ROLLOUT-MANIFEST.md); отправитель/ключи/Vault не меняются автоматически. Текущий check-supabase.sql проверяет 18 функций и один trigger; прежние 10 функций относились к preview.8.

Turn Push сверяется с текущим владельцем права действия; старые и завершённые ходы удаляются до отправки. Промежуточные действия того же игрока и реконнект не создают дубликат. Ботам/зрителям ход не отправляется. Одновременные игры поддерживают несколько игроков с доступными обычными действиями. При открытом приложении социальные события показываются коротким сообщением внутри приложения; в фоне — системным Push. Нажатие на игровое событие открывает комнату, на сообщение — чат.

### Приоритет доставки

Пользовательские Push отправляются с `urgency: high`: запрос на немедленную доставку провайдеру. Это не гарантия показа или сроков на устройстве. После изменения приоритета функция отправителя развёртывается отдельно; обновление клиента и смена VAPID-ключей не нужны. Получение на телефоне проверяется отдельно от успешного ответа Push-провайдера.

## Только явно запрошенные важные обновления

Рассылки об обновлениях не связаны с build, release, deploy или cron. Отправлять их можно **только после прямого поручения владельца разослать именно это важное обновление**. Просьба собрать/выпустить версию такого разрешения не даёт. Получатели — текущие устройства аккаунтов, явно включивших уведомления. Доставка и переход поддерживаются клиентом preview.46 и новее.

Операторская команда `server/push/announce-update.mjs` по умолчанию выполняет только локальный dry-run:

```sh
node server/push/announce-update.mjs --project-ref geurlwivdiqboylciqhl --version 0.20.0 --title 'Важное обновление' --body 'Краткое описание причины обновления'
```

Только после прямого поручения добавить `--env-file /private/path/playroom-push.env --send`. Файл должен быть доступен лишь владельцу. Секрет никогда не передаётся аргументом и не печатается. Веб-клиенты не имеют доступа к операторскому RPC. Версия защищена от повторной рассылки; повтор с другими заголовком/текстом завершается конфликтом. Событие актуально семь дней. Нажатие открывает окно обновлений; установка остаётся явным действием и не прерывает текущую партию.
